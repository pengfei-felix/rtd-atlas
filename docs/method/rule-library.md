# 规则库设计

## 必然膨胀

规则库的膨胀不是管理不善，是结构性的：每出现一个新异常，现场就加一条 if-then。产能爬坡期 + 多产品混线 + 异常频发的阶段，规则数量会失控（成熟 DRAM 厂光刻区 200+ 条属常态），优先级互相冲突，调一个指标必定牺牲另一个。

**这不是算法问题，是 Know-How 积累方式的问题**——也是国产 RTD 与国际一线产品的真实差距所在，不是算法代差。

## 三条控制手段

| 手段 | 作用 | 代价 |
|---|---|---|
| **分层** | 全局规则 / 区域规则 / 临时规则分开，临时规则带过期时间 | 需要有人定期清理 |
| **冲突检测** | 规则上线前做两两冲突扫描，检测优先级倒挂 | 需要形式化描述规则的作用对象 |
| **指标绑定** | 每条规则必须挂一个可观测的验证指标，无指标不得上线 | 前期工作量大，但能挡住 80% 的随意加规则 |

## 规则 vs 优化的边界

纯规则在单一产品、稳定期的新厂够用。一旦进入多产品混线和异常频发期，就该把一部分规则替换为优化模型——但**不是全替换**。可行的路径是分区、分层替换：先换最独立的那一段，保留规则做兜底。
