# G4 · 稳定性治理

<div class="keyline" markdown>

**RTD 每 30 秒重算一次。如果没有冻结期和改派门槛，它会把一个 Lot 从 A 机挪到 B 机，再挪回来。** 计划本身可能每一步都更优，但现场会疯掉——操作员刚搬过去的东西又被改回去了。

</div>

## 核心结论

1. **最优计划 ≠ 可执行计划。** 改派有成本，成本不进模型，系统就会过度优化。
2. **冻结期是必须的，不是妥协。** 已开始的 run、已搬送到位的 Lot、已预留的资源，都不该被重算推翻。
3. **override 不是失败，是数据。** 禁止 override 的系统一定会被绕过；不记录 override 的系统永远学不会。
4. **规则要有退出机制。** 只有上线没有下线的规则库，最后会变成没人敢碰的黑箱。
5. **8 寸和 12 寸在这件事上难度不同。** 12 寸的指令是命令，8 寸的指令是建议。

## 冻结期

| 冻结对象 | 冻结到什么时候 | 理由 |
|---|---|---|
| 已 track-in 的 Lot | 加工结束 | 物理上不可能改 |
| 已搬送到机台 port 的 Lot | 上料完成 | 改派等于多一次搬送 |
| 已锁定辅助资源的 Lot | 资源释放 | Reticle 已经在机台上 |
| 已被下游预留的走廊 | 预留兑现或超时 | 否则预留形同虚设 |
| 刚被派工、尚未执行的 Lot | 短冻结窗（分钟级） | 防止系统抖动 |

最后一条最容易被忽略。派工结果下发到 EAP 到实际执行之间有一个时间差，这段时间如果重算，会出现「指令打架」——EAP 收到了两条矛盾的指令。

### 冻结窗设多长

| 场景 | 建议 |
|---|---|
| 全自动 12 寸 | 一个搬送周期 + 上料时间，通常 10~20 分钟 |
| 半自动 / 8 寸 | 一个班次内的最短操作间隔，可以更长 |
| 异常期间（机台宕机） | 临时缩短，允许快速重排 |

冻结窗设太长，系统失去应变能力；设太短，指令打架。这个参数必须按实际搬送节拍标定，不能拍脑袋。

## 改派门槛

不是所有改派都值得做。收益必须超过成本：

```text
改派收益 = 新方案目标值 - 当前方案目标值
改派成本 = 额外搬送时间
         + 重新 setup 损失
         + 辅助资源重配代价
         + 操作员认知成本
改派条件：改派收益 > 改派成本 × 安全系数
```

`安全系数` 建议取 1.2~1.5。留余量是因为模型对收益的估计通常偏乐观，对成本的估计通常偏保守。

### 什么时候允许突破门槛

只有两种情况：

1. **P0/P1 触发**：硬约束被违反，或者走廊即将 breach。
2. **人工授权**：带授权人和原因，事后必须复核。

除此之外一律不突破。允许"特殊情况特殊处理"的系统，最后所有情况都是特殊。

## Override 策略

### 三种 override

| 类型 | 场景 | 系统应做什么 |
|---|---|---|
| **修正型** | 系统信息不全，现场更清楚 | 接受，记录缺失字段 |
| **规避型** | 操作员图省事、怕麻烦 | 接受但计数，高频需干预 |
| **冲突型** | 规则之间打架，操作员被迫选 | 接受并告警，这是规则缺陷的信号 |

区分这三种，比统计 override 次数有用得多。**冲突型 override 是规则库的 bug 报告**，出现就该去查规则，而不是去批评操作员。

### 必填字段

| 字段 | 说明 |
|---|---|
| `override_reason` | 从固定选项里选，不允许自由文本 |
| `override_by` | 工号或账号 |
| `original_decision` | 系统原本推荐了什么 |
| `actual_decision` | 实际做了什么 |
| `outcome` | 事后回填：结果好/坏/无差异 |

`outcome` 是唯一能让规则库学习起来的字段。大部分厂只记前四个，所以 override 数据只能用来考核，不能用来改进。

!!! tip "8 寸的关键差异"
    12 寸有全自动 AMHS，派工指令会被执行，override 是例外事件。

    8 寸大量靠人工搬送和上下料，override 是常态。**在 8 寸，override 回写不是 nice-to-have，是一等公民**——不接这个，"实际执行了什么"系统根本不知道，规则库永远在拿假设喂自己。

## 规则生命周期

| 阶段 | 门槛 | 责任人 |
|---|---|---|
| 提出 | 有现场症状 + 数据证据 | 提出人 |
| 建模 | 对象、条件、动作、指标齐全 | 区域 owner |
| 回放 | 历史数据验证，副作用可量化 | RTD owner |
| 灰度 | 影子模式或小范围 | RTD owner |
| 全量 | 指标改善 + 无重大副作用 | 联合评审 |
| 复审 | 定期看命中率、贡献、冲突数 | 区域 owner |
| 下线 | 命中率过低、指标无改善、被替代 | 区域 owner |

### 下线条件

规则下线比上线重要，也更难推动——没人愿意承认自己加的规则没用。

| 条件 | 动作 |
|---|---|
| 临时异常已解除 | 自动过期，不需要人批 |
| 连续 N 期命中率为 0 | 标记待复审，走归档 |
| 指标无改善 | 回滚 |
| 副作用超阈值 | 立即停用 |
| 被更高层模型覆盖 | 标记 deprecated，保留追溯 |

**临时规则必须有 `valid_until`。** 没有过期时间的临时规则，是所有规则库里最危险的一类——它们通常验证最少、最容易和其他规则冲突，而且没人记得它为什么在那。

## 典型问题

### 问题 1：系统抖动，Lot 反复改派

| 项 | 内容 |
|---|---|
| 现象 | 同一个 Lot 在几台机之间来回跳，操作员拒绝执行 |
| 根因 | 没有冻结期和改派门槛，每次重算都是全局最优 |
| 解法 | 冻结窗 + 改派门槛 + 滞回 |
| 指标 | reassignment rate、指令冲突数 |

### 问题 2：override 数据只能考核不能用

| 项 | 内容 |
|---|---|
| 现象 | override 率居高不下，但不知道为什么 |
| 根因 | 只有原因码，没有结果回填 |
| 解法 | 加 `outcome` 字段，分类统计三类 override |
| 指标 | override rate 按类型拆分、冲突型占比 |

### 问题 3：临时规则永久化

| 项 | 内容 |
|---|---|
| 现象 | 三年前为某次异常加的规则还在生效 |
| 根因 | 没有 `valid_until`，审批时也没人问 |
| 解法 | 临时规则强制过期，续期需重新审批 |
| 指标 | 有效临时规则数、超期未复审数 |

### 问题 4：影子模式跑得很好，一上就崩

| 项 | 内容 |
|---|---|
| 现象 | 影子期指标漂亮，切换后现场抵触 |
| 根因 | 影子模式不执行，所以没暴露执行层问题 |
| 解法 | 灰度阶段必须真执行，只是范围小 |
| 指标 | 灰度期 override 率、执行偏差率 |

## 指标体系

| 层级 | 指标 | 说明 |
|---|---|---|
| 主指标 | 计划执行率 | 系统推荐被实际执行的比例 |
| 约束指标 | reassignment rate、指令冲突数 | 防止靠抖动换指标 |
| 观测指标 | override rate（分类）、冻结窗命中、临时规则数 | 定位治理问题 |

**计划执行率是通用层的总指标。** 它掉下去，说明规则再优化也没用——现场已经不听了。
