# 通用规则层 · 总览

<div class="keyline" markdown>

**通用层是"每个区都要用的那部分规则"。** 九个区都要排序，逻辑本来就一样，差的是参数；把这部分提炼成一份放在上层，各区**加载**它，再追加自己的工艺特化。所以是**一层托着一层**，不是两套并列的规则，也不是并列的第十个区。

</div>

## 这一层装什么

两类东西都放这里，进入的理由不同：

| 类型 | 判断方式 | 例子 | 在区域层怎么出现 |
|---|---|---|---|
| **共性基础规则** | 每个区都要用，逻辑相同、参数不同 | 优先级继承、老化升权、setup 损失、下游可接性、冻结期 | 直接继承，**改参数** |
| **跨区规则** | 单个区看不到全貌，或必须全厂唯一 | Q-time 走廊预算、辅助资源池、污染隔离、瓶颈漂移 | 无参数可调，**照全局执行** |

第一类是主体。很多人做通用层只做第二类，结果每个区还是各写一套排序逻辑——那等于没有通用层，只是加了个仲裁器。

## 为什么必须单独成层

区域档案里各写一遍排序和 Hot Lot，是最常见的做法，也是最容易烂的做法。四个理由：

| 理由 | 后果 |
|---|---|
| **基础排序本来就是同一套** | 九个区各写一份 EDD/FIFO/老化，等于维护九份同源代码，改一次漏八处 |
| **冲突仲裁必须集中** | Hot Lot 撞上 Q-time 红区谁压谁，是全局判断。九份分散的规则，改一次策略要改九处 |
| **瓶颈会漂移** | 这月 Litho 堵，下月变 CMP。「瓶颈优先」写死在任何一个区里都是错的 |
| **有些规则不属于任何区** | Q-time 走廊横穿 Clean → Litho → Etch → Diffusion，单一区看不到整条链 |

## 三层关系：加载 → 覆写 → 特化

区域层不是"另写一套"，是在通用层上长出自己那一层。按顺序三步：

```text
① 加载   继承通用层全部规则：硬约束过滤、优先级序列、老化、setup 估算、下游可接性
② 覆写   只改参数：阈值、权重、时间常数、批量上下限、抽样比例
③ 特化   追加通用层算不出来的：Reticle 双锁、组炉、pad 退化、bath 寿命、载具池
```

**① 和 ② 不允许改逻辑，③ 不允许复制通用层的逻辑。** 这条界线一破，通用层就会退化成一份没人看的模板，九个区各跑各的。

## 准入标准

一条规则要进通用层，满足**任意一条**即可：

1. **每个区都要用，逻辑相同**（共性基础）→ 放通用层，参数在区域层覆写；
2. **作用对象跨两个区以上**（走廊、资源池、污染）→ 放通用层，唯一一份；
3. **必须全厂唯一确定**（优先级等级、冻结期、污染等级）→ 放通用层，不许多份；
4. **需要跨区数据才能计算**（走廊余量、瓶颈位置）→ 放通用层，因为区内算不出来。

四条都不满足的，一律留在区域层。这条标准要写进规范，否则通用层会变成垃圾桶——谁都往里塞，最后没人敢动。

!!! warning "覆写失控比双轨更隐蔽"
    如果九个区把同一个参数各覆写一遍，通用层的默认值就等于失效了，但它看起来"还在用"。

    两条对策：**覆写要登记**（哪条、改成多少、为什么），以及**同一个参数被三个以上区覆写，说明默认值本身是错的**——回通用层改默认值，不要在区里继续叠。

!!! warning "临时双轨的代价"
    通用层不是一天能建完的。G2（时间窗走廊）和 G3（资源与污染）依赖链路数据和资源台账，投入大、见效慢。

    先跳过是可以的，但必须在文档里标成**临时双轨**并设补期——各区的 Q-time 规则先自己维护一份。永久双轨比一开始就不做更糟：两套逻辑同时生效，现场会以为系统在随机决定。

## 仲裁序列

通用层独立出来后，必须配套一条显式优先级序列。它写在 G1 里，但约束全部九区。

```text
P0  硬约束         qualification / 污染隔离 / 不合格机台
P1  Q-time 红区    即将超时，余量低于安全线
P2  Hot Lot        按等级继承，跨区不衰减
P3  瓶颈优先       当前瓶颈区的队列优先供料
P4  常规排序       setup 最小化 / WIP 平衡 / 老化升权
```

没有这条序列，通用规则和区域规则冲突时，日志里看起来就是"系统随机决定"。P0 到 P4 之间不允许被权重覆盖，只允许被更高优先级覆盖。

**P4 是基线，P0–P3 是全局判断。** 每个区加载 P4 后按自己的参数覆写（谁更该等、setup 值多少），但 P0–P3 的判定标准各区不许动——动了就等于把全局优先级改成了局部优先级。

## 和区域层怎么配合

| | 通用层 | 区域层 |
|---|---|---|
| 和对方的关系 | 被九个区**加载**的基础规则 | **加载 + 覆写参数 + 追加特化** |
| `scope` | 所有区 | 本区 / tool group |
| 回答的问题 | 谁优先、能不能放、什么时候不许改 | 这个区里哪台机、哪个腔体、什么顺序 |
| 允许改什么 | 逻辑（版本化发布） | 只许改参数；逻辑改动必须回通用层 |
| 维护人 | RTD owner + 计划 | 区域 owner |
| 变更频率 | 低，版本化发布 | 中，随工艺调整 |
| 冲突时 | 高优先级胜出，且必须留痕 | 低优先级降权或丢弃 |

区域层的详细规则见 [区域派工档案](../zones/index.md)；规则字段标准和生命周期见 [规则库设计](../method/rule-library.md)，那页讲的是"一条规则怎么管"，这页讲的是"规则分几层、谁管谁"。

## 落地顺序

不是四个模块同时上。按这个顺序走，前期投入产出比最高：

| 阶段 | 做什么 | 理由 |
|---|---|---|
| 一期 | G1 + G4 | 不需要跨区数据打通，靠现有字段就能配，且立刻能解释现场 90% 的"为什么派它" |
| 二期 | G3 | 依赖辅助资源台账，先把 Reticle / Pod / Boat / Pad 的状态接齐 |
| 三期 | G2 | 依赖完整链路数据，最重，但也最容易出效益 |

一期做完，通用层就已经能撑住日常派工；G2 没上之前，Q-time 规则先在区域层临时维护，按上文标注双轨。
