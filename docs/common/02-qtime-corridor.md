# G2 · 时间窗走廊

<div class="keyline" markdown>

**区域层管"这一段窗口在本区怎么快"，通用层管"整条链的时间预算怎么分"。** 前者是局部加速，后者是全局分配。只做前者，会出现每个区都不超时、串起来却超时的局面。

</div>

!!! note "和跨幅专题的分工"
    走廊**为什么会断**、链条长什么样、入口限流和下游预约的思路，见 [Q-time 走廊](../topics/qtime-corridor.md)。

    这页讲的是另一件事：这些逻辑在通用层里**怎么落成规则和字段**——对象怎么定义、预算怎么分、冲突怎么裁、超时之后降级成什么。

## 核心结论

1. **走廊是一等对象，不是窗口的集合。** 它要有自己的 ID、自己的剩余预算和自己的状态。
2. **硬窗和软窗必须分开建模。** 混在一起，系统会把"可以商量的"和"绝对不能破的"同等对待。
3. **余量要预留，不是到时候再抢。** 等红了再动手，只剩插队和返工两条路。
4. **超时之后的动作要事先定义。** 没定义，现场就自己发明一套。
5. **走廊的优先级高于区域优化。** 这是 P1 压 P3 的直接来源。

## 硬窗与软窗

| 类型 | 判定 | 违反后果 | 派工处理 |
|---|---|---|---|
| **硬窗（Hard）** | 工艺物理极限，超时即报废或必须返工 | 不可逆 | 只能预留和限流，不允许"赌一把" |
| **软窗（Soft）** | 质量风险随超时时间上升，非绝对 | 可评估、可让步 | 红区提权，黄区预警，允许有授权记录的放行 |
| **管理窗（Admin）** | Fab 自己设的节拍要求 | 无物理后果 | 可降权处理，不应占用 P1 |

把管理窗当硬窗配，是最常见的过度约束——系统会为了一个没有物理依据的时限打断合理排程，操作员很快就会开始习惯性 override。

## 走廊对象的字段

| 字段 | 说明 |
|---|---|
| `corridor_id` | 唯一标识，跨区不变 |
| `corridor_steps` | 有序的 (step, area, hard/soft, limit) 序列 |
| `corridor_start_event` | 计时起点，通常是上一道的出片事件 |
| `total_budget` | 整条链的总预算 |
| `remaining_budget` | 实时余量，每次状态变化都要刷新 |
| `reserved_downstream` | 已为下游预留的产能或时段 |
| `escalation_level` | green / yellow / red / breached |

`remaining_budget` 必须由通用层维护。让各区各自算，边界上一定对不齐——A 区以为还剩 40 分钟，B 区按自己那段的起点算出来是 25 分钟，两边都"合规"，实际已经超了。

## 余量分配

预算不是均分。三种分法，按链路特点选：

| 分法 | 适用 | 做法 |
|---|---|---|
| **等分** | 各段耗时接近、波动小 | 总预算 ÷ 段数，简单但脆弱 |
| **按基线加权** | 各段耗时差异大 | 按历史 P50 耗时占比分配，留公共缓冲 |
| **按波动加权** | 某段波动特别大 | 波动大的段多分余量，稳定段少分 |

第三种最实用。走廊断掉，八成断在波动最大的那一段，而不是总耗时最长的那一段。

### 公共缓冲

不分给任何一段的余量，用来吸收突发事件。经验值取总预算的 10%~15%。

公共缓冲由通用层持有，任何区域规则都不能直接动用——只能通过 `reserve` 动作申请，且必须记录申请人。否则每个区都会觉得"反正还有缓冲"，缓冲会在一小时内被分光。

## 下游产能预留

这是走廊能成立的前提。派工不是"我现在做完了交给下游"，而是"我现在做，下游在 X 分钟后必须有位置"。

| 预留对象 | 预留什么 | 失效处理 |
|---|---|---|
| 下一站机台时段 | 一个时间槽 | 超时未用则释放，记录预留命中率 |
| 下一站辅助资源 | Reticle / Pad / 载具 | 同上 |
| 量测能力 | 一个 metrology slot | 高优先级走廊优先 |

**预留命中率是这条规则的核心指标。** 低于 70% 说明预留太粗或执行不稳，走廊会持续断。

## 超时降级

必须事先定义，不能临时决定：

| 阶段 | 状态 | 动作 |
|---|---|---|
| 余量 > 40% | green | 正常排序 |
| 余量 15%~40% | yellow | 提权，检查下游预留是否生效 |
| 余量 < 15% | red | P1，可打断低优先级 run，锁定下游 |
| 已超时 | breached | 按工艺定义走：返工 / 特采 / 报废 / 强制量测 |

`breached` 之后的分支一定要写死在规则里。四种处置的经济后果差一个数量级，让现场自由裁量，等于把工艺决策交给操作员。

## 与区域层的分工

| | 通用层（G2） | 区域层 |
|---|---|---|
| 走廊定义 | 建对象、管预算 | 只读 |
| 余量计算 | 统一口径 | 只读 |
| 本段加速 | — | 排序时优先安排临近红区的 Lot |
| 下游预留 | 发起和仲裁 | 提供可预留产能 |
| 超时分支 | 定义处置策略 | 执行具体工艺动作 |

一条判断标准：**凡是需要知道"这个 Lot 从哪来、后面还有几站"的，归通用层；只需要知道"这一段还有多少时间"的，归区域层。**

## 典型派工问题

### 问题 1：单段全绿，链条断裂

| 项 | 内容 |
|---|---|
| 现象 | 每个区都显示合规，Lot 到末端已经超时 |
| 根因 | 各区按自己那段的起点计时，起点不统一 |
| 解法 | 走廊起点由通用层统一定义，余量统一计算 |
| 指标 | 走廊 breach 率 vs 单窗 violation 率的差值 |

### 问题 2：抢救性插队把下一个窗口挤爆

| 项 | 内容 |
|---|---|
| 现象 | 一段救回来了，下一段立刻超时 |
| 根因 | 出口没有防传染机制 |
| 解法 | 提权时同步检查下游预留，挤爆则降级为 hold |
| 指标 | 连续两段同时红区的事件数 |

### 问题 3：预留了大量产能但没命中

| 项 | 内容 |
|---|---|
| 现象 | 下游频繁预留，实际到货时间差很远 |
| 根因 | 预留按计划时间而非实际 ETA |
| 解法 | 用 AMHS ETA 和机台实际剩余加工时间算预留时刻 |
| 指标 | reservation hit rate、reservation drift |

### 问题 4：管理窗当硬窗，打断合理排程

| 项 | 内容 |
|---|---|
| 现象 | 系统频繁为了软性时限拆分稳定 run |
| 根因 | 窗口类型没区分 |
| 解法 | 三类窗口分开配置，只有 hard 进 P1 |
| 指标 | 管理窗触发占比、因管理窗产生的中断次数 |

## 落地路线

这是四个模块里最重的一个，不建议一期就上全量。

1. **先建走廊对象**：把跨区 Q-time 按链路整理成有 ID 的走廊，标清楚每段是硬窗还是软窗。
2. **统一计时起点**：这是最容易忽略、也最容易出错的一步。起点不统一，后面的余量计算全是错的。
3. **接下游预留**：从最常断的那一两条走廊开始，只做预留，不做提权。
4. **加提权与降级**：确认预留命中率稳定在 70% 以上再加，否则提权只是让问题往前挪。
5. **回放验证**：用历史数据比较 breach 率、插队次数、返工率，三条一起看。只看 breach 率会诱导系统过度插队。
