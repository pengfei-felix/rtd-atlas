# G1 · 优先级与排序

<div class="keyline" markdown>

**优先级是全厂唯一的，不是每个区各排一份。** 一个 Lot 在 Litho 是 Hot，到 CMP 变成 Normal，这种事只要发生过一次，现场就不会再相信系统给的顺序。

</div>

## 核心结论

1. **Hot Lot 的等级跨区继承，不衰减。** 降级只能由计划明确下达，不能由区自己决定。
2. **瓶颈位置是动态变量，不是常量。** 写死在规则里，产品组合一变就失效。
3. **本区有空不等于能放。** 下游接不住，放过去只是把排队位置换个地方。
4. **等太久的 Lot 必须自动升权。** 否则低等级 Lot 会在队列里饿死，最后集中爆出来。
5. **仲裁序列必须是显式的。** 隐含在代码里的优先级，等于没有。

## Hot Lot 分级

| 等级 | 来源 | 跨区行为 | 附加约束 |
|---|---|---|---|
| **Super Hot** | 客户急件、工程验证 | 全厂最高，可打断常规 run | 必须记录授权人 |
| **Hot** | 订单交付风险 | 跨区继承，不衰减 | 受 Q-time 红区压制 |
| **Rework** | 返工批 | 高于同等级正常 Lot | 单独计数，避免掩盖返工率 |
| **Normal** | 常规生产 | 按 P4 排序 | — |
| **Fill** | 填炉、填批 | 最低，可被随时替换 | 不得占用关键辅助资源 |

两条容易做错的：

- **Rework 不应该混在 Normal 里排序。** 返工批带质量风险，插在稳定 run 中间会破坏工艺连续性，表面上还看不出问题。
- **Fill Lot 不能占用稀缺资源。** 用 Reticle 去跑填炉批，等于拿瓶颈资源换利用率。

## 瓶颈识别与漂移

瓶颈不是设计产能最低的区，是**实际负荷最高的区**。判定方法见 [瓶颈判定](../zones/bottleneck.md)，这里只讲规则怎么配。

| 字段 | 说明 |
|---|---|
| `bottleneck_area` | 当前瓶颈区，按时段滚动计算 |
| `bottleneck_confidence` | 判定置信度，负荷率接近时需要 |
| `recalc_window` | 重算周期，建议小时级，不按季度 |
| `hysteresis` | 切换门槛，防止瓶颈在边界来回跳 |

`hysteresis`（滞回）这条必须要有。两个区负荷率分别是 91% 和 90% 时，如果没有切换门槛，系统会每半小时换一次瓶颈，派工策略跟着抖。

### 瓶颈优先的具体动作

| 对象 | 动作 |
|---|---|
| 瓶颈区队列 | 供料优先，减少饥饿时间，不打断已开始的 run |
| 非瓶颈区 | 按瓶颈消耗速度投料，队列设上限 |
| 瓶颈区的上游 | 提前备料，缩短瓶颈等料时间 |
| 瓶颈区的下游 | 预留接收能力，防止瓶颈出片即堵 |

非瓶颈区的目标函数里必须出现"不超过队列上限"这一项。只写"最大化利用率"，系统一定会把 WIP 推到瓶颈门口。

## 下游可接性

派工当下最容易犯的错：本区有台机空着，就把 Lot 排上去，不管下游接不接得住。

| 检查项 | 数据来源 | 不检查的后果 |
|---|---|---|
| 下一站是否有合格机台 | 工艺路线 + 机台资质 | Lot 到了下一站排队，本区空转收益被抵消 |
| 下一站 Q-time 余量 | Timelink 计算 | 本区快了，下一站超时 |
| 下一站辅助资源 | Reticle / Pad / boat 状态 | 到了没资源，只能等 |
| 搬送能力 | AMHS ETA | 出片了 FOUP 送不走 |

这条规则的技术难点不在判断，在**深度**。看一站还是看三站，取决于派工周期和工艺路线长度。经验做法：跨关键 Q-time 节点的，至少看两站。

## 老化升权

队列里的 Lot 等太久会饿死。老化机制给等待时间一个正向权重：

```text
priority_score = base_priority
               + hot_lot_weight
               + bottleneck_weight
               + aging_factor( waiting_time )
               - setup_penalty
               - downstream_risk_penalty
```

| 参数 | 典型处理 |
|---|---|
| `aging_factor` | 分段线性，不是一条斜线到底 |
| 起点 | 该产品正常等待时间的 1.5~2 倍 |
| 上限 | 不得超过 Hot Lot 权重，否则优先级失效 |
| 清零 | Lot 被派工后归零，重入下一站重新计 |

**上限这一条很关键。** 老化权重如果没上限，一个等了三天的 Normal Lot 会压过刚进来的 Hot Lot，现场立刻炸。

## 典型派工问题

### 问题 1：Hot Lot 在某个区被降权

| 项 | 内容 |
|---|---|
| 现象 | 同一个 Lot 在 A 区优先，到 B 区排到队尾 |
| 根因 | 各区自己维护优先级表，没有统一来源 |
| 解法 | 优先级由通用层唯一发布，区域只读 |
| 指标 | hot lot cycle time 分段统计、跨区优先一致性 |

### 问题 2：瓶颈判定滞后

| 项 | 内容 |
|---|---|
| 现象 | 瓶颈已经转移，派工还在按老瓶颈供料 |
| 根因 | 瓶颈按周/月计算，或者只看理论产能 |
| 解法 | 滚动窗口重算 + 滞回门槛 |
| 指标 | 瓶颈判定与实际队列排行的偏差、瓶颈饥饿时间 |

### 问题 3：只看一站，下游爆掉

| 项 | 内容 |
|---|---|
| 现象 | 本区吞吐提升，全厂周期时间变长 |
| 根因 | 派工不检查下游可接续性 |
| 解法 | 下游可接性检查，覆盖关键 Q-time 节点 |
| 指标 | 下一站等待时间、跨区超时率 |

### 问题 4：老化权重压过 Hot Lot

| 项 | 内容 |
|---|---|
| 现象 | 急件排不进去，被老批挡住 |
| 根因 | 老化系数无上限，或与 Hot Lot 同量纲累加 |
| 解法 | 老化权重设绝对上限，且低于 Hot Lot 权重 |
| 指标 | hot lot wait、priority inversion count |

## 字段清单

| 字段 | 类型 | 说明 |
|---|---|---|
| `lot_priority_class` | enum | super_hot / hot / rework / normal / fill |
| `priority_source` | string | 谁授的权，用于追责和审计 |
| `bottleneck_area` | string | 当前瓶颈区 |
| `bottleneck_confidence` | float | 0~1，低置信时降级为不启用瓶颈权重 |
| `downstream_check_depth` | int | 下游检查站数 |
| `aging_start` / `aging_cap` | duration | 老化起算点和上限 |
| `arbitration_trace` | list | 命中/压制了哪些规则，冲突时必填 |

## 派工规则骨架

```text
对每个候选 Lot：
  1. 读 lot_priority_class（通用层唯一来源）
  2. 若命中 P0 硬约束 → 直接过滤
  3. 若位于 Q-time 红区 → 提到 P1，跳过 P2~P4
  4. 检查 downstream_check_depth 站内的可接续性
  5. 计算 priority_score（含 bottleneck、aging、setup、下游风险）
  6. 按 P3/P4 排序，输出候选序列
  7. 写入 arbitration_trace：谁命中、谁压制、为什么
```

第 7 步不是可选的。没有 trace，规则冲突时无法归因，只能靠人吵。
