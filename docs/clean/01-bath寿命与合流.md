# Bath 寿命与批式合流

<div class="keyline" markdown>

**Bath 是"看不见的退化资源"。** Pad 磨薄了能测出来，bath 什么时候不行了，只能靠片数累计加抽检猜。状态可信度低，就意味着派工要留更保守的余量。

</div>

## 为什么 bath 比 pad 难管

| 维度 | Pad | Bath |
|---|---|---|
| 可观测性 | 厚度、粗糙度可测 | 只能靠累计 + 抽检 |
| 退化形态 | 连续磨损 | 化学能力衰减，非线性 |
| 更换代价 | 换 pad，分钟级 | 换液 + 升温稳定，小时级 |
| 失效表现 | 去除率漂移 | 残留、颗粒、腐蚀 |

三个后果：

1. **状态字段一定不准。** 系统里的 bath age 是估算值，不是实测值。
2. **换液窗口必须提前。** 不能在快要不行的时候才换，要在还能用的时候主动换。
3. **末期余量要更宽。** 保守系数比 pad 高。

## 计量与分段

| 计量方式 | 适用 | 优缺点 |
|---|---|---|
| 处理片数 | 通用 | 简单，但忽略片型差异 |
| 累计浸泡时间 | 时间敏感型药液 | 更准，但数据难采 |
| 浓度分析 | 关键槽体 | 最准，需要在线分析仪 |
| 颗粒计数 | 循环过滤系统 | 反映实际能力 |

多源数据不一致时，取**最保守**的一边。这不是谨慎，是必要条件——bath 状态本来就有不确定性，乐观取值等于赌。

### 分段

| 阶段 | 剩余 | 处理 |
|---|---|---|
| Fresh | 100% → 80% | 关键层优先，能力最好 |
| Stable | 80% → 30% | 正常派工 |
| Warning | 30% → 10% | 限制关键层，准备换液 |
| End-of-life | < 10% | 只跑非关键 / dummy，或直接换液 |

Fresh 段值得单独拎出来：关键层（尤其是小尺寸图形）应该在 freshest 的 bath 上做，这是用调度换良率的直接手段。

## 批式合流

### 合流的三条约束

| 约束 | 说明 | 强度 |
|---|---|---|
| 化学体系一致 | 同一槽只能接受同一类药液流程 | 硬 |
| 产品 / 层限制 | 部分产品不能混批 | 硬 |
| 装载率 | 槽容量利用率 | 软，可欠载 |

前两条过滤，第三条优化。**装不满可以走，这是和炉管组炉最大的区别**——炉管欠载的代价是整炉时间浪费，清洗槽欠载主要是水和化学品的浪费。

### 欠载判定

```text
如果 等待下一批的时间 > 该批走廊余量的安全比例
   → 欠载出发
否则
   → 等待合流
```

关键在"走廊余量"。一批不急的 Lot 值得等，一批已经进入紧窗口的 Lot 不值得等。**合流决策必须看下游，不能只看装载率。**

### 合流优先级

| 优先级 | 对象 |
|---|---|
| 1 | 已进入 P1 走廊的 Lot（可单独开槽） |
| 2 | Hot Lot |
| 3 | 同化学体系、可填满的常规批 |
| 4 | 填槽批（dummy / 非关键） |

第 1 条容易被忽略：系统为了省一槽药液，让一个快超时的 Lot 等了 40 分钟，省下的成本远小于超时的损失。

## 换液调度

换液是主动行为，不是被动触发。

| 触发方式 | 时机 | 问题 |
|---|---|---|
| 按片数上限 | 到达阈值 | 滞后，末期已经跑了一批风险批 |
| 按状态分段 | 进入 Warning 末段 | 较优，可结合生产计划 |
| 按计划窗口 | 结合 PM 和低负荷时段 | 最优，但需要跨部门协同 |

**最优做法是把换液安排在低负荷时段。** 换液本身要占 1~4 小时（排空、清洗、配液、升温、验证），在高峰时段换液等于自减产能。

## 典型问题

### 问题 1：末期跑关键层

| 项 | 内容 |
|---|---|
| 现象 | 换液前最后几批残留或颗粒超标 |
| 根因 | 只设片数上限，没有 warning 段 |
| 解法 | 分段限制，warning 段起禁止关键层 |
| 指标 | bath-end defect rate |

### 问题 2：为装满而让急件等

| 项 | 内容 |
|---|---|
| 现象 | 合流决策只看装载率，走廊 breach 增加 |
| 根因 | 合流目标函数缺走廊约束 |
| 解法 | 余量不足时允许欠载出发 |
| 指标 | batch-induced breach count |

### 问题 3：多源状态不一致时取了乐观值

| 项 | 内容 |
|---|---|
| 现象 | 片数说还能跑，颗粒计数已经报警 |
| 根因 | 没有冲突处理规则 |
| 解法 | 多源取最保守，且记录冲突 |
| 指标 | bath state conflict count |

### 问题 4：换液撞上生产高峰

| 项 | 内容 |
|---|---|
| 现象 | 高峰时段整槽停机换液，下游全部等 |
| 根因 | 换液被动触发，不看生产节奏 |
| 解法 | 换液窗口与负荷曲线联动，提前排 |
| 指标 | bath downtime during peak |

## 字段清单

| 字段 | 说明 |
|---|---|
| `bath_id` | 槽体唯一标识 |
| `chemical_system` | 化学体系分类，用于硬隔离 |
| `capacity` | 批容量（片数） |
| `age_metric` | 当前累计值及计量单位 |
| `age_source` | 片数 / 时间 / 浓度 / 颗粒，多源时列表 |
| `segment` | fresh / stable / warning / eol |
| `next_change_plan` | 计划换液时刻 |
| `allowed_products` | 允许的产品 / 层列表 |

## 一条实操建议

**先做"谁能进这个槽"的过滤，再做"什么时候出发"的优化。**

前者的收益是防事故，后者的收益是提吞吐。顺序反了，会在一个还没搞清污染隔离的槽体上做组批优化——优化出来的结果本身就可能是违规的。
