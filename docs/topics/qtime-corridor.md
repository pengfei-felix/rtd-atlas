# Q-time 走廊

<div class="keyline" markdown>

**Q-time 不是一个个独立的闹钟，是一条走廊。** 一个 Lot 要穿过几十个时间窗，前一个窗口里多等十分钟，下一个窗口就少十分钟。**单段都合规、串起来超时**，是现场最难查的一类问题。

</div>

## 窗口 vs 走廊

| 视角 | 看什么 | 后果 |
|---|---|---|
| **窗口视角** | 每个 Q-time 单独校验，超没超 | 段段合规，全程不合格 |
| **走廊视角** | 一段工序序列的**累计时间预算** | 能提前看到"再这样下去会在哪爆" |

派工系统默认都是窗口视角——因为窗口是硬约束，好写规则。但真正决定 Q-time 违规率的，是走廊视角。

## 走廊长什么样

一条典型路径上的窗口并非均匀分布，有的紧、有的松，而且**紧密窗口往往串在一起**：

```
清洗 ──[紧]── 光刻 ──[紧]── 刻蚀 ──[中]── 去胶 ──[松]── 量测 ── …
          ↑                    ↑
       不能久等            腐蚀风险
```

紧密窗口串联的区域，就是走廊上最容易堵的路段。

## 三种失效模式

<div class="grid cards" markdown>

-   :material-alert-circle-outline:{ .lg .middle } __① 单点超时__

    ---

    某个窗口直接被撑爆。

    **特征**：偶发、集中、容易定位。

    **成因**：设备宕机、料未到、插单。

    处理简单，但只占少数。

-   :material-chart-bell-curve-cumulative:{ .lg .middle } __② 累积挤压__

    ---

    每一段都在窗口边缘运行，没有余量。

    **特征**：违规率不高但持续，一有扰动就成片爆。

    **成因**：投料过密、队列长度失控。

    这是**最常见也最难改**的一类。

-   :material-swap-vertical-bold:{ .lg .middle } __③ 优先级倒挂__

    ---

    加急批插队，把已进入窗口的普通批挤出去。

    **特征**：普通批违规，加急批达标。

    **成因**：Hot Lot 判据只看到期时间，不看走廊占用。

    这是**管理问题伪装成调度问题**。

</div>

## 派工能做什么

### 策略一：走廊容量管理

限制**同一时刻处于窗口内的 Lot 数量**。走廊像一段有车道的路，同时挤进去的车超过容量，必然有人超时。

具体做法：给每个紧密路段设一个在窗上限，达到上限时，上游的 Lot 在"安全的等待点"多待一会儿——**宁可让它在窗口外等，也不要让它进窗口后堵着**。

### 策略二：反向排程

不要从"现在"往后推，从**窗口截止时刻倒推**：这批必须在什么时刻之前到达哪个节点，倒推出最晚开工时间。

正向排程只知道"什么时候能做完"，反向排程才知道"最晚什么时候必须开始"。

### 策略三：分级预警

| 级别 | 判据 | 动作 |
|---|---|---|
| 绿 | 剩余时间 > 半个窗口 | 正常排队 |
| 黄 | 剩余时间 < 半个窗口 | 提升优先级，锁定下一台机 |
| 红 | 剩余时间 < 安全阈值 | 抢占、专机专送、通知值班 |

关键是**黄色阶段就要动作**。等到红色才处理，能选的手段只剩"插队"，而这正是失效模式③的来源。

## 五个常见错误

1. **只在快到点时处理。** 那时能做的只有插队，代价转嫁给别人。
2. **把 Q-time 当纯硬约束，不问来源。** 每个窗口背后都有物理原因（氧化、腐蚀、光阻硬化）。不知道原因，就没法判断"超一点到底有多严重"，也没法做优先级排序。
3. **各区独立计算。** 走廊跨区，光刻段的拥挤会在刻蚀段引爆。
4. **不区分 Lot 级与 Wafer 级管控。** 粒度不同，算法完全不同。
5. **用"剩余时间最短优先"做派工。** 会导致频繁切换机台，换线成本反而吃掉收益。
