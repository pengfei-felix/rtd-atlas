# 辅助资源流转

<div class="keyline" markdown>

**辅助资源的调度粒度，决定了 RTD 的真实能力上限。** 只对机台建模的 RTD，最多能做到"机台有活干"；把辅助资源也建进去，才可能做到"机台到点就有料"。

</div>

## 四种共享模式

同样是"辅助资源"，共享方式不同，派工策略完全不同。**用错模式比不建模更糟。**

| 模式 | 特征 | 例子 | 派工策略 |
|---|---|---|---|
| **独占型** | 同一时刻只能被一处使用，用完释放 | Reticle、专用夹具 | 提前锁定 + 搬运前置 |
| **成组型** | 资源按组绑定，一组一起锁 | Pod（内含多张光罩） | 组内组合优化，避免连带锁死 |
| **退化型** | 使用会消耗寿命，性能连续下降 | Pad、石英件 | 建连续状态，避免集中用到末期 |
| **消耗型** | 用完即弃，需补货 | 靶材、Slurry、特种气体 | 库存水位 + 补货周期进模型 |

## 流转拓扑

以光刻区的 Reticle 为例，一张罩从库房到机台要走五个环节：

```
裸罩库 BRS
   │  ① 检查 / 洁净
   ▼
Pod 装载（同 Layer Type 才能同 Pod）
   │  ② Pod 入库
   ▼
Pod Stocker
   │  ③ 天车搬运（OHT）
   ▼
机台 Tool Library（典型容量约 10 张）
   │  ④ 满库需先卸载
   ▼
机台使用
```

**四个环节，任何一处排队，机台就在空转。** 而 RTD 传统上只看最后一个环节——机台有没有可加工的 Lot。

## 卡点在哪

| 卡点 | 机制 | 表现 | 谁能解 |
|---|---|---|---|
| **① 检查能力** | 光罩使用后需按周期检查 | 罩回不来，下一轮用不了 | 检查机台的产能规划 |
| **② Pod 数量** | 每种 Layer Type 的专属 Pod 数固定 | 直接构成该层的并行机台上限 | 采购决策，派工改不了 |
| **③ 搬运运力** | OHT / Stocker 的吞吐有限 | 高峰期搬不过来 | AMHS 调度，不是 RTD |
| **④ 库位容量** | Tool Library 满库要先卸 | 需要的罩装不进 | RTD 要设 buffer 水位触发清库 |

!!! warning "② 是硬件约束，派工无法绕过"
    Pod 数量固定意味着**该 Layer 的并行度有物理上限**。如果 RTD 不知道这个上限，会排出"三台机同时跑同一层"的计划——物理上做不到，因为只有两组 Pod。这类计划在现场表现为"机台等罩"，RTD 侧却显示"已派工"。

## 一个必须记住的判断

> **辅助资源的调度，不能作为派工的"事后补丁"。**

常见的错误架构是：RTD 先决定 Lot 上哪台机，然后再去要 Reticle / Pad。这样做出来的计划有两个必然后果：

1. **冲突无法消解**，只能靠现场人工协调；
2. **搬运时间被事后加上**，计划与实际的偏差越滚越大。

正确做法是**联合决策**：Lot 派工与辅助资源分配在同一时刻、同一模型里决定，搬运时延进目标函数。

## 备选策略：牺牲柔性换确定性

Nexperia 的现场做法值得记：**每种 Layer Type 最多同时分配给 2 台机台**。

这是一条极其朴素但有效的硬约束——用牺牲一点灵活性，换掉大量 Reticle/Pod 冲突。它不优雅，但在 Pod 数量受限的环境里，比任何复杂的优化都稳。

这类"人为收紧约束"的做法在派工系统里很常见，判断标准只有一条：**收紧带来的是不是确定性，如果换来的是可预测，就值得。**
