# Metrology 量测区派工档案

<div class="keyline" markdown>

**量测有两个身份：它占用产能，是瓶颈候选；它产出数据，是其他区的输入。** 只按第一个身份排，量测会被当成"服务部门"排在所有加工之后；按两个身份排，才知道有些量测比生产还急。

</div>

## 核心结论

1. **不是每批都量。** 采样规则决定排队结构，比机台产能更影响拥堵。
2. **recipe 时长差异极大。** 同一台机跑不同 recipe，单片时间可能差十倍。
3. **量测是数据源，不是收尾工序。** R2R 和 feedback 都靠它，排太晚等于让上游瞎跑。
4. **缺陷检测是另一个物种。** 并入本区，但 recipe 长度、抽样逻辑、瓶颈行为都不同。
5. **量测机台数量少，但被所有区依赖。** 它自己不一定是瓶颈，却经常是"最后一脚"。

<div class="rtd-strip" markdown>

<span>决策粒度</span> Lot → Tool → Recipe  
<span>核心矛盾</span> 等待时间 vs 数据新鲜度 vs 机台产能

</div>

## 与其他区的结构差异

| 维度 | 加工区 | Metrology | 差异要点 |
|---|---|---|---|
| 加工目的 | 改变晶圆状态 | **读取状态，不改变** | 失败不报废，只损失时间 |
| 批量性 | 有批次概念 | 通常单片 | 一片一片量 |
| 时长 | 相对稳定 | **recipe 间差 10 倍** | 排程必须按 recipe 算 |
| 产出 | 产品 | **数据** | 数据有保质期 |
| 优先级依据 | Lot 优先级 | Lot 优先级 **+ 数据紧急度** | 两套依据 |
| 失败后果 | 返工 / 报废 | 重测 | 代价低但时间成本真实 |

最后一条容易被低估：量测失败不毁片，所以常被认为"不重要"。但量测占用的机台时间是硬的，堵起来和加工区一样堵。

## 六类约束结构

### 1. 采样规则

| 采样类型 | 触发 | 排队影响 |
|---|---|---|
| 全检 | 关键层、新产品、异常后 | 全部进队列 |
| 固定比例 | 每 N 批抽一批 | 可按批预测 |
| 事件触发 | 参数调整后、PM 后、override 后 | **突发**，最难预测 |
| 动态采样 | 按 SPC 状态调整 | 需要与 SPC 联动 |

**事件触发采样是排队的主要不确定性来源。** 它不按计划来，而且往往集中在异常期间——正是产能最紧张的时候。

### 2. Recipe 与机台资质

| 约束 | 说明 |
|---|---|
| recipe 与机台能力匹配 | 不是每台机都能跑每个 recipe |
| 校准状态 | 过期未校准不能用于关键层 |
| 标准片 / 参考片 | 部分 recipe 需要，占用额外资源 |
| 环境要求 | 温度、振动敏感设备有额外限制 |

### 3. 两种身份下的优先级

| 身份 | 优先级依据 |
|---|---|
| 消费者 | Lot 优先级、走廊余量 |
| **生产者** | **数据紧急度**：谁在等这份数据 |

数据紧急度怎么算：

```text
数据紧急度 = 下游等待方的重要性 × 数据过期的后果
```

举例：一批 CMP 跑完等量测才能定下一批参数。这份数据不到，CMP 只能停机等或者盲跑。此时量测的紧急度高于它作为 Lot 的优先级。

### 4. 缺陷检测的特殊性

| 项 | 量测 | 缺陷检测 |
|---|---|---|
| recipe 时长 | 分钟级 | **十分钟到数小时** |
| 抽样 | 按点位 | 全片扫描或抽片 |
| 结果 | 数值 | 图像 / 缺陷图谱 |
| 瓶颈行为 | 平稳拥堵 | **长 recipe 造成尖峰** |

一条数小时的检测 recipe 占着机台，等于几个小时没有产能。排这种活必须提前，不能插在中间。

### 5. 数据新鲜度

| 字段 | 说明 |
|---|---|
| `data_age` | 距上次同 product/layer 的有效量测 |
| `stale_threshold` | 超过多久数据失效 |
| `consumer` | 谁在等这份数据（CMP R2R / TF 反馈 / SPC） |

数据过期的后果不是绝对的，取决于消费者：CMP 的 R2R 对新鲜度最敏感，SPC 相对宽松。

### 6. Inline 与 Offline

| 形态 | 特点 | 派工处理 |
|---|---|---|
| Inline | 在流程中间，不量不能走 | 硬约束，队列优先级高 |
| Offline | 抽到单独区域量，不阻塞主线 | 可按产能灵活排 |
| 8 寸常见 | 离线为主，人工送片 | 有额外搬运与等待 |
| 12 寸常见 | inline 密集 | 量测插在每几道工序之后 |

这条是 8 寸和 12 寸差异最大的地方之一：12 寸的量测在流程里，跑不掉；8 寸的量测可以攒着一起送，反而更灵活但也更容易漏。

## 典型派工问题

### 问题 1：量测排队拖垮下游 R2R

| 项 | 内容 |
|---|---|
| 现象 | CMP 参数靠猜，因为量测结果迟迟不到 |
| 根因 | 量测只按 Lot 优先级排，不看数据消费者 |
| 解法 | 引入数据紧急度，等数据的批次提权 |
| 指标 | data wait time、R2R blind run count |

### 问题 2：长 recipe 插在高峰

| 项 | 内容 |
|---|---|
| 现象 | 一条缺陷检测排进去，后面几小时全堵 |
| 根因 | 排程按 Lot 数算产能，不按 recipe 时长 |
| 解法 | 按 recipe 实际时长算占用，长 recipe 提前排 |
| 指标 | queue jump loss、长 recipe 时段分布 |

### 问题 3：量测成为隐性瓶颈

| 项 | 内容 |
|---|---|
| 现象 | 各加工区都跑得动，出货卡在量测 |
| 根因 | 量测机台少且被当服务，不计入瓶颈判定 |
| 解法 | 量测纳入瓶颈计算，按 recipe 加权算负荷 |
| 指标 | metrology utilization（按 recipe 加权） |

### 问题 4：8 寸漏量

| 项 | 内容 |
|---|---|
| 现象 | 该量的没量，事后追溯发现数据缺口 |
| 根因 | 离线量测靠人工送，没有强制校验 |
| 解法 | 量测需求进 Lot 状态，未完成不能过站 |
| 指标 | sampling miss rate |

## 派工规则骨架

```text
当 metrology tool 预计空闲：
  1. 枚举候选（含等待中的量测需求）
  2. 过滤机台资质 / 校准状态 / 环境要求
  3. 按 recipe 实际时长估算占用
  4. 计算两个分数：
       lot_urgency（Lot 优先级 + 走廊余量）
       data_urgency（等待方的关键度 × 过期后果）
  5. 取两者较高者作为最终优先级
  6. 长 recipe 单独处理：提前排，不插高峰
  7. 检查是否阻塞主线（inline 且未量不能走 → 硬提权）
```

第 5 步的"取较高者"是刻意的。用加权平均会让两边都得不到足够权重——要么急件等数据，要么数据等急件。

## 指标体系

| 层级 | 指标 | 用途 |
|---|---|---|
| 主指标 | 有效量测片数、数据准时率 | 看它对全流程的贡献 |
| 约束指标 | sampling miss、校准过期使用、queue jump loss | 防止靠偷采样提产能 |
| 观测指标 | data age、recipe 时长分布、inline 阻塞时长 | 定位拥堵来源 |

## 落地路线

1. **先做资质与校准过滤**：纯硬约束，最容易做，也最防事故。
2. **把 recipe 时长接进来**：从"按片数"改成"按时长"算产能，这一步收益最明显。
3. **引入数据紧急度**：接上 CMP / TF 的等待方，量测优先级才算完整。
4. **长 recipe 单独排程**：缺陷检测与常规量测分开处理。
5. 回放验证：data wait、queue jump loss、量测利用率三条一起看。
