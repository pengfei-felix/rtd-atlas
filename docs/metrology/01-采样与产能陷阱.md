# 采样规则与产能陷阱

<div class="keyline" markdown>

**量测的产能不是一个数，是一组数。** 报"每天能测 800 片"没有意义，因为跑什么 recipe 决定了它实际能吃多少。按片数排量测，是所有隐性瓶颈的共同起源。

</div>

## 陷阱一：按片数算产能

同一台机，两种 recipe：

| Recipe | 单片时间 | 8 小时能测 |
|---|---|---|
| 膜厚（快速点位） | 3 分钟 | 约 160 片 |
| 缺陷扫描（全片） | 90 分钟 | 约 5 片 |

差 30 倍。如果产能按"平均 8 分钟/片"估算，一条缺陷扫描排进去，当天计划就废了。

### 正确算法

```text
有效产能 = Σ (各 recipe 可用时长 ÷ 该 recipe 单次时长)
```

而不是：

```text
有效产能 = 总可用时长 ÷ 平均单次时长    ← 错
```

前者需要知道未来的 recipe 组合。这也是为什么量测区的瓶颈判定要特别小心——它的负荷率会随 recipe 组合剧烈波动。

## 陷阱二：动态采样造成突发

采样规则本身会变：

| 触发 | 采样变化 |
|---|---|
| SPC 报警 | 从抽检变全检 |
| 新 recipe 上线 | 前若干批全检 |
| PM 后 | 恢复期加密 |
| 客户投诉 / 异常调查 | 临时全检 |

这些变化都在**最忙的时候**发生——异常期本来产能就紧，采样量还上去了。

工程含义：量测区的产能规划不能按稳态算，要按**峰值**算。稳态刚好够用的量测产能，一遇异常就崩。

## 陷阱三：事件触发无法预测

| 采样类型 | 可预测性 | 排程方式 |
|---|---|---|
| 固定比例 | 高，可按批推算 | 正常排 |
| 全检 | 高 | 正常排 |
| 事件触发 | **低** | 预留缓冲产能 |

事件触发的量测（参数调整后、override 后、返工后）没有提前量。做法是留一块**机动产能**，不排常规活。

机动产能的比例参考：10%~15%。低于这个数，一遇异常就排不进去；高于这个数，量测机台利用率上不去。

## 陷阱四：把 inline 当 offline 排

| 形态 | 不量的后果 | 优先级 |
|---|---|---|
| Inline | **Lot 不能走**，整条线停 | 硬提权，等同 P0 |
| Offline | Lot 可以走，数据后补 | 按产能灵活排 |

把 inline 的量测当普通队列排，会出现"料卡在量测前，机台在后面等"。这类拥堵在报表上表现为量测区排队，实际根因是排程没区分形态。

## 陷阱五：数据生产者的身份被忽略

量测有两个产出：**片（通过）** 和 **数据**。第二个常被漏掉。

| 消费者 | 在等什么 | 等不到会怎样 |
|---|---|---|
| CMP R2R | 上一批厚度 | 盲跑，参数靠猜 |
| TF 反馈 | 膜厚结果 | 参数滞后，可能批量偏 |
| SPC | 趋势数据 | 报警延迟 |
| 工程分析 | 特定批次数据 | 分析阻塞 |

**盲跑（blind run）是这里最贵的失败模式。** 一台 CMP 不知道上一批结果就继续跑，出来的可能是一串废片，而不是一片。

### 数据紧急度怎么定

```text
data_urgency = f(consumer_criticality, stale_penalty, waiting_time)
```

| 参数 | 说明 |
|---|---|
| `consumer_criticality` | 消费者是硬闭环（CMP R2R）还是软监控（SPC） |
| `stale_penalty` | 数据过期后的损失量级 |
| `waiting_time` | 已经等了多久 |

硬闭环消费者应该有接近 P2 的优先级，即使它对应的 Lot 本身是 Normal。

## 陷阱六：校准与标准片占用

| 占用项 | 频率 | 影响 |
|---|---|---|
| 日常校准 | 每班 / 每天 | 固定占用，可预测 |
| 标准片测量 | 定期 | 占用机台但不产出 |
| 匹配验证 | PM 后 | 突发占用 |
| 环境恢复 | 振动、温度事件后 | 不可预测 |

这部分产能必须从可用产能里扣掉，不能算进"可排产"。常见的错误是校准时间在事后被记录，排程时却没扣。

## 一份可用的量测产能台账

| 字段 | 说明 |
|---|---|
| `tool_id` | 机台 |
| `recipe_id` | recipe |
| `cycle_time` | 单次时长（实测，不是标称） |
| `setup_time` | recipe 切换代价 |
| `qual_status` | 是否 qual，校准是否有效 |
| `available_hours` | 扣除校准、标准片后的可用时长 |
| `flex_reserve` | 留作事件触发的机动产能 |

按这张表算出来的产能，才是能用来排程的产能。

## 典型问题

### 问题 1：平均时长估算，长 recipe 打爆计划

| 项 | 内容 |
|---|---|
| 现象 | 计划排得好好的，一条缺陷检测进来全乱 |
| 根因 | 产能按平均时长算 |
| 解法 | 按 recipe 组合算，长 recipe 提前排 |
| 指标 | plan deviation、长 recipe 排队时长 |

### 问题 2：异常期采样暴增压垮量测

| 项 | 内容 |
|---|---|
| 现象 | SPC 报警期间，量测排不上，加工区等 |
| 根因 | 产能按稳态规划 |
| 解法 | 按峰值规划 + 预留机动产能 |
| 指标 | 异常期 data wait、flex reserve 消耗率 |

### 问题 3：盲跑没被识别

| 项 | 内容 |
|---|---|
| 现象 | 一串片子参数全偏，追查发现是没等量测 |
| 根因 | 数据紧急度不在派工里 |
| 解法 | 硬闭环消费者的数据提权，盲跑计入指标 |
| 指标 | blind run count、blind run 后的不良率 |

## 一条实操建议

**先量一遍自己的 recipe 时长分布，再谈量测产能。**

大部分厂对量测产能的认知停留在"几台机"这个层面，对 recipe 时长分布没有实测数据。没有这个分布，任何排程优化都是猜。

这件事成本很低——从机台日志里拉一个月的实际 cycle time，按 recipe 分组做个分布就行。做完之后，很多"产能不够"的抱怨会自动消失，因为会发现瓶颈是某两三个长 recipe，而不是整体。
