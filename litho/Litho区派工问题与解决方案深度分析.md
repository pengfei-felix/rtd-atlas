# Litho 区派工问题与解决方案深度分析

> 视角：半导体生产制造 / RTD·APS 排程系统工程
> 编制日期：2026-10-23
> 适用对象：8"/12" 前道晶圆厂光刻区派工逻辑设计、RTD 规则库重构、CIM 供应商选型评估

---

## 0. 核心结论（先看这段）

1. **Litho 不是"派工难"，是"三体问题"。** 其他区派工只解一个方程：`哪个 Lot 上哪台机`。Litho 要同时解三个耦合方程：`Lot → 机台`、`Reticle(+Pod) → 机台`、`机台 → 温层/Recipe 状态`。三者任一不到位，机台就空转。这是 Litho 派工与炉管、刻蚀、离子注入在**问题结构上的本质差异**，不是难度差异。

2. **80% 的 Litho 白空间（white space）不是产能不足，是"料到了罩没到"。** 行业公开结论一致指向这一点：Lot 到达机台但所需 Reticle 仍被别的机台锁定，或仍在 Stocker / 检查流程里。解法不在算法而在**预测窗口**——必须提前 10~15 分钟把 Reticle 搬送指令和 Lot 搬送指令一起发出去。

3. **规则库会必然膨胀到失控。** 头部 DRAM 厂光刻区 RTD Rule 数量 200+ 条属常态，优先级互相冲突，调一个指标牺牲另一个。纯规则（if-then）路线在产品单一的新厂够用，到**产能爬坡期 + 多产品混线 + 异常频发**的成熟期必然崩。这是国产 RTD 与 AMAT 的真实差距所在——**不是算法代差，是 Rule 库 Know-How 的积累代差**。

4. **"调度 vs 派工"必须分层，且 RTD 要有推翻 RTS 的权力。** WSC 2025 的仿真验证结论：RTD 完全服从 RTS 计划时，吞吐量下降超过 50%；阈值设在 5 分钟左右时吞吐量最优。RTD 沦为 RTS 的"传声筒"是国内很多厂的实际状态，机台宕机了还在等计划重排。

5. **选型时只看 MES 是选错了维度。** MES 各家差距有限，**RTD 才是拉开差距的模块**，而 Litho 区是 RTD 能力的唯一真实试金石。供应商如果拿不出 Litho 区的 Reticle 协同派工实绩，其 RTD 基本只是"带 UI 的优先级排序器"。

6. **收益量级（公开数据锚点）**：Litho 区机台利用率 +1%~2%、吞吐 +2%~9.4%、Reticle Move 可同时 -5%、Queue Time -4%。注意这些数字横跨 2011~2025 年、不同基线、不同厂型，**不能当承诺值，只能当量级参考**。

## 一、Litho 区的八重约束结构（问题根源解剖）

Litho 的调度问题在学术上被归为**柔性作业车间 + 重入工艺 + 驻留时间约束的强 NP-hard 问题**；更精确的建模是「**不相关并行机 + 序列相关与机台相关整定时间 + 机台资格约束 + 辅助资源及其搬运时间**」（Nexperia 案例的 CP 建模表述）。下面把八重约束逐条拆开，这是设计任何派工逻辑的前置清单。

### 约束 1：重入流（Re-entrant Flow）—— Litho 是全厂的物流配送中心

- 单片 Wafer 在整条流程里要**反复返回 Litho 区 18~40 次**（逻辑/存储 20~35 层，ASIC 高混线可达 40 层）。
- 一座 12" 厂同时在产批次 >10000 批、单片约 300 道工序、数百种设备。
- **工程含义**：Litho 区队列里的 Lot 来自**所有不同层、不同产品、不同优先级**，而不是像单向流水线那样来自单一上游。任何只看"当前队列"的派工规则都会失真——队列构成每 15 分钟就换一副面孔。
- 台湾交大早期的 PADR 研究已经把黄光区定位为"整个晶圆制造的物流配送中心"，这个定位比"瓶颈设备"更准确。

### 约束 2：辅助资源双层嵌套（Reticle + Pod）—— 最被低估的约束

这是 Litho 独有、且**国产 RTD 最常做漏**的一层。

| 层级 | 约束内容 | 派工影响 |
|---|---|---|
| Reticle | 因开发成本高，**每张光罩通常唯一**（unique），不可复制 | 同一层的多台机台在物理上争抢同一张罩 |
| Pod | Reticle 装在 Pod 里成组搬运；**Pod 一旦上机，Pod 内全部 Reticle 只能被该机台使用** | 一次错误的 Pod 分配会连带锁死多张罩 |
| Pod 组合规则 | 只有**同 Layer Type** 的 Reticle 才允许装入同一 Pod；每种 Layer Type 的专属 Pod 数固定 | Pod 数量直接构成该 Layer 的并行机台上限 |
| Tool Library | 机台内置光罩库**典型容量 10 张**；满库需先卸载才能装新罩 | 库容量成为隐性约束，需要 buffer level（如 8/10 触发清库） |
| 搬送时间 | Reticle/Pod 跨机台转移有 transfer time；Pod Stocker ↔ BRS（裸罩库）↔ Tool Library 三级流转 | 搬送时间必须进目标函数，否则排出来的计划物理不可行 |

**Nexperia 的现场做法值得记**：为规避 Reticle/Pod 冲突，**每种 Layer Type 最多同时分配给 2 台机台**。这是一条极其朴素但有效的硬约束——用牺牲一点灵活性换掉大量冲突。

> ⚠️ **高频设计错误**：把 Reticle 建模为"可用/不可用"的布尔量。正确建模是**带位置、带容量上限、带搬运时延、带寿命计数的受限资源**。前者会让 RTD 排出大量"看起来可行、实际做不到"的派工。

### 约束 3：机台专属性（Machine Dedication）—— 与负载均衡天然对立

- **关键层（critical layer）必须在同一台机上做完**，以控制套刻（overlay）误差；非关键层可放开。
- 重工（rework）的 Lot **通常也要回到原机台**。
- Dedication 分级（1-level / 2-level / 3-level）直接决定产能柔性：
  - Virginia Tech 的 DRAM 产线仿真（240 工序 / 18 光刻层）给出一条反直觉结论：**无 PM/宕机场景下 3-level dedication 最优；一旦引入确定性的宕机与 PM 排程，1-level dedication 反而最优**。
- **工程含义**：Dedication 柔性不是越高越好。**柔性的价值取决于你的设备可靠性水平**。可靠性差的产线放开 Dedication，等于把宕机风险放大传导到更多批次。

### 约束 4：机台能力不等（Unrelated Parallel Machines）

- 同型号机台的加工时间受 **stepping speed、light intensity、每片 flash 总数** 影响，差异显著。
- 不是每台机都有资格跑每个 Job（machine eligibility / process capability）。
- **图形精度分级（pattern precision）** 构成嵌套能力：高精度机台组可以跑低精度活，反之不行 → 典型的**非对称资格矩阵**。
- **这是国产 RTD 的常见盲点**：把同型号机台当等效并行机处理，忽略 machine-reticle 配对带来的加工时间差。Nexperia 实测数据：短 Job 均值 598s / σ=39s，长 Job 均值 2479s / σ=282s，**差异 4 倍以上**，且需按「机台 × Reticle」配对统计才有意义。

### 约束 5：序列相关整定时间 —— 换罩 + 温层

国内 CN103390538B 专利把这个问题讲得最透：

- 不同 Recipe 所需的光罩温度不同，换罩后机台需要**为下一片曝光的光罩升温或降温**，这种等待**恒定且耗时**。
- 该专利的解法是引入**「温层值」（自然数）**，按温层差排序：
  - 对每个制程设定温层值
  - 计算 `待处理温层值 − 当前温层值`
  - 结果为正 → 直接取差值；结果为负 → **加上最大温层值**（即建模为环形升温序列，降温代价远高于升温）
  - 温层差越小，优先级越高
- 这条设计很有现场味道：**它把物理过程（升降温不对称）编码进了排序函数**，而不是简单地"同 Recipe 优先"。

**整定时间的三层结构**（设计派工公式时要分开算权重）：

| 层级 | 触发条件 | 典型代价 |
|---|---|---|
| L1 无整定 | 同 Reticle 连续加工 | ≈ 0 |
| L2 库内换罩 | 同 Pod / 同 Layer 内换罩，温层相近 | 短 |
| L3 跨机搬罩 + 换温层 | 需 Pod 搬送 + 升降温 | 长，且占用 ARHS 运力 |

### 约束 6：Q-time / Timelink 的嵌套约束

- Q-time 定义：上一工序 Track-out 到下一工序 Track-in 的等待时间，必须落在 `[min, max]` 区间。
- 管控粒度分 **Lot 级**（Load Port 出 → 下一设备 Load Port 到）与 **Wafer 级**（回 Carrier → 下一设备抽片）。
- Litho 相关的典型窗口：镀膜→光刻 ≤ 4h；显影→刻蚀、刻蚀→清洗 ≤ 2h；特殊工艺甚至 30min。
- **最难的是嵌套 Timelink（nested timelink）**：Step2→Step4 有一个窗口，Step3→Step4 还有一个重叠窗口，Step3 的排程必须同时满足两个约束。实际产线上是**数百个工序、大量重叠窗口**同时在跑。
- 违规后果：轻则清洗返工，重则整批报废（单次损失可达百万量级）。

**死锁场景（最考验 RTD 功底）**：机台宕机，已到达该工序的批次 Q-time 开始倒计时。RTD 要在秒级决策——等维修（预计 30min 恢复）还是转备机（工艺参数有差异，需重做 SPC 验证）？

### 约束 7：量测与重工回路

- Litho 后必过量测：**Overlay（套刻对位）+ CD（关键尺寸）**。
- 判 NG → 回 Litho 重工，且**重工优先回原机台**。
- **工程含义**：Litho 的实际负载 = 正常曝光 + 不可预测的重工量。重工率的波动直接表现为产能的随机波动，**派工逻辑必须为重工预留产能缓冲**，否则重工一来就挤爆正常排程。

### 约束 8：光罩寿命与检查限 —— 隐形停机源

IBM 的自动化光罩管理专利（US7953507 / CN100416577C）把这套管得最细：

- 光罩检查限按**曝光次数**计量，分两级：
  - **Warning Limit**：接近需检查的参考点
  - **Inhibit Limit**：必须检查前的最大允许曝光次数（硬卡控）
- 派工必须考虑 **projected inspection limit**（预测检查限）：别把一张马上要送检的罩装上机台跑大批量。
- 该专利的 Reticle 派工决策因子清单，可直接当设计 checklist：
  1. Tool Library 容量（典型 10）
  2. Reticle 派工优先级
  3. Tool 临界容量缓冲水平（如 8/10 触发清库）
  4. Reticle 检查限（warning + inhibit）
  5. 预测检查限
  6. **未来 Lot 的 WIP 预测**（含：罩件号、关联批次数、预测到达/完成时间窗、最高优先级、前瞻顺序号）
  7. 基于 **ARHS 运力**的单次移动请求数量 N

> 第 7 条尤其重要：**Reticle 搬送指令不能无限下发**，必须按自动光罩搬运系统的实际运力节流，否则指令堆积、全部延迟。

## 二、九个核心派工问题（问题 → 根因 → 症状 → 解法 → 验证指标）

### 问题 1：Reticle Lock-down 导致的白空间

| 项 | 内容 |
|---|---|
| **现象** | Lot 已到机台，Reticle 不在位；或某张罩被柔性高的机台锁住，而柔性低的机台马上要饿死 |
| **根因** | 派工决策只看"当前"Reticle 位置，不看未来 10~15 分钟的 Lot 到达与机台空闲 |
| **代价** | 行业公认这是 Litho 白空间的**首要来源** |
| **解法核心** | **前瞻性 Reticle 预分配**：基于 WIP 到达预测，提前把 Reticle 搬送指令和 Lot 搬送指令**配对下发** |
| **进阶** | 引入"**机台柔性度**"权重：当多台机可用同一张罩时，**优先把罩留给柔性最低的机台**（柔性高的机台有替代活可干） |
| **指标** | Reticle Wait Idle Time（机台因等罩的空转时长）、Reticle Move 次数、Litho OEE |

**可直接落地的规则骨架**：
```
对每台即将空闲的机台 M（预测空闲时刻 t_free）：
  1. 枚举候选 Lot 集合 L = { 已在队列 } ∪ { 预测在 t_free ± Δ 到达 }
  2. 过滤：machine_eligibility(M, L) ∧ dedication_ok(M, L) ∧ qtime_feasible(L, t_free)
  3. 对每个候选 Lot l 计算总代价：
     Cost(l) = w1·温层差(M, l)
             + w2·Reticle搬送时延(l, M, t_free)      // 罩在位则 0
             + w3·Reticle移动惩罚(l)                  // 跨机搬罩惩罚
             + w4·(1 / 机台柔性度(l))                 // 柔性低者优先拿罩
             + w5·Q-time剩余紧迫度(l)                 // 越紧迫越优先
             + w6·优先级权重(l)                       // hot lot
             + w7·线平衡偏差(l)                       // 层间 WIP 均衡
             - w8·同罩连续批数(l)                     // 奖励批量聚集
  4. 若 min Cost 对应 Lot 需搬罩，且 ARHS 运力未饱和 → 同时下发 Lot + Reticle 搬送指令
  5. 校验 Reticle 剩余曝光次数 > 本批所需曝光数（否则跳过并触发送检）
```

### 问题 2：Machine Dedication 与负载均衡的死结

| 项 | 内容 |
|---|---|
| **现象** | 关键层批次全压在 2~3 台"金机台"上排长队，其他同型号机台闲置 |
| **根因** | Dedication 是**良率硬约束**，不可为产能让步；但 Dedication 记录往往是"一次写死、从不复核" |
| **解法 1** | **分级 Dedication**：按层的套刻敏感度分 1/2/3 level，而不是全厂一套标准 |
| **解法 2** | **按设备可靠性动态调节 Dedication 柔性**——这是关键洞察：可靠性低的机群收紧 Dedication，可靠性高的放开 |
| **解法 3** | 建立 **Dedication 解绑流程**：机台宕机超过阈值时，自动触发"解绑申请 + SPC 验证"流程（不是直接放行，而是把人工审批工程化） |
| **解法 4** | 在 **MILP/CP 层**把 dedication 作为硬约束、把 max machine load 作为最小化目标（CAPPA 模型的标准做法） |
| **指标** | 各机台负载标准差、关键层 Dedication 命中率、因 Dedication 造成的额外排队时长 |

**CAPPA 模型（Bosch 案例）的标准形式**，可作为 Litho 产能分配层的建模模板：

```
目标：min  max_m ( machine_load_m )          // 最小化最大机台负载（削峰）
约束：
  (a) machine process capability    —— 机台对 Recipe 的资格
  (b) machine dedication            —— 关键层同机
  (c) maximum reticle sharing       —— 单张罩在不同层间共享次数上限
已证明为 NP-hard；CPLEX 可解小规模，大规模用改进 GA（IRGGA，含启发式初始种群）
```

### 问题 3：换罩/温层整定时间被低估

| 项 | 内容 |
|---|---|
| **现象** | 实际产出持续低于理论产能 5%~15%，但找不到明显停机 |
| **根因** | 派工公式里**没有次序相关整定时间项**，或只按"同 Recipe/不同 Recipe"二值处理 |
| **典型反模式** | 「Recipe 切换整定时间不建模 → 高估性能；Recipe 数增多即整定时间增大」（调度理论教材明确列为反模式） |
| **解法 1** | 引入 **温层值模型**（见约束 5）：把升温/降温的不对称性编码进排序 |
| **解法 2** | **时间窗组批**：在时间窗内把同罩/同层批次聚集连跑，窗宽可参考 `Δt = 0.5 × ΣP_i /(B·M)` 的量级思路 |
| **解法 3** | 做成 **Campaign（战役）模式**：按 Layer Type 给机台分配 4 小时级的"主攻层"，窗内只做该层（Nexperia 现场做法），机台故障或恢复时重评估 |
| **陷阱** | 组批过度 → Hot Lot 和 Q-time 批次被饿死。必须设**组批上限**和**饥饿保护**（队列中 Lot 等待超 X 分钟强制插入） |
| **指标** | 换罩次数/班、平均整定时间占比、同罩连跑平均批数、Setup Loss |

### 问题 4：Q-time 约束下的调度死锁

| 项 | 内容 |
|---|---|
| **现象** | 机台宕机 → 下游 Litho 前的批次 Q-time 集体告急 → 要么批量 Hold 返工，要么硬转备机引入良率风险 |
| **根因** | Q-time 管控与派工决策**分属两个系统**，Q-time 只做"超时报警"，没进派工目标函数 |
| **解法 1** | **Q-time 剩余时间进排序权重**，且用**非线性**权重（剩余 <20% 时权重陡升），避免线性权重下仍被 Hot Lot 压过 |
| **解法 2** | **嵌套 Timelink 的可行性预检**：派工前校验该决策是否会使任一嵌套窗口不可行；不可行则直接剔除候选（CP 建模的标准做法） |
| **解法 3** | **宕机场景的决策树工程化**：`预计修复时长 vs Q-time 剩余 vs 备机 Recipe 等效性 vs SPC 验证耗时` 四因子，提前把决策表写进系统，而不是现场拍脑袋 |
| **解法 4** | **源头减量**：对高风险 Timelink 的工序对，在投料/排程层就限制同时在窗批次数 |
| **公开成效锚点** | Renesas 扩散区案例：优化排程使 **Timelink 违规降低 29%** |
| **指标** | Q-time 违规次数、因 Q-time 的 Hold/Scrap 数、嵌套窗口可行性预检拦截数 |

### 问题 5：重工与量测回路造成的优先级倒挂

| 项 | 内容 |
|---|---|
| **现象** | 重工批次挤占正常排程；或重工批次因"优先级低"长期压在队列底部，拖垮整批交期 |
| **根因** | 重工 Lot 的优先级往往按原优先级继承，但它的**剩余工序价值**已经变化（已投入成本更高、交期更紧） |
| **解法 1** | 重工 Lot 优先级**独立计算**：按 `已投入层数 × 交期紧迫度` 升权，而不是沿用原级别 |
| **解法 2** | 重工回原机台的约束 → 在 Reticle 预分配时**为重工预留窗口**（原机台的罩别急着搬走） |
| **解法 3** | **为重工预留产能缓冲**：按历史重工率（含波动）在产能模型中扣减，而不是用理论产能排程 |
| **指标** | 重工批平均等待时长、重工回原机台命中率、重工造成的额外 Litho 负载占比 |

### 问题 6：Hot Lot 插队的雪崩效应

| 项 | 内容 |
|---|---|
| **现象** | Hot Lot 开绿灯 → 常规批排队更久 → WIP 膨胀 → 下一班 Hot Lot 更多（恶性循环） |
| **根因** | 三个目标天然矛盾：吞吐（机台不停）、CT（单批快速通过）、WIP（库存不高不低）。给 Hot Lot 让路必然牺牲另两个 |
| **关键认知** | 这**不是参数调一调就好的问题，是真正的多目标优化问题**。TWT / OTD / MCT / UOB / Makespan **不可能同时最优** |
| **解法 1** | **显式选主指标**，其余设为约束（而非同权目标）。例：主目标 min 加权总拖期，约束 Litho OEE ≥ X% |
| **解法 2** | **Hot Lot 配额制**：按班次限定 Hot Lot 数量/占比上限，超配需升级审批。治本在源头而非派工 |
| **解法 3** | 差异化收益验证：AMAT 公开数据显示，优化排程使**最高优先级批 CT 改善 ~20%，次高 <5%，低优先级不变**——这正是"目标函数起作用"的证据形态，也说明 Hot Lot 收益是**从低优先级批次借来的** |
| **指标** | 分优先级 CT（必须分层统计，总平均会掩盖问题）、Hot Lot 占比、常规批 CT 恶化幅度 |

### 问题 7：规则库膨胀与冲突

| 项 | 内容 |
|---|---|
| **现象** | 光刻区 Rule 200+ 条，优先级关系梳理需要两名工程师全职；每加一条要评估与现有全部 Rule 的冲突；每次工艺变更要改一批 |
| **根因** | 纯 if-then 规则引擎的**组合复杂度随 Rule 数呈超线性增长**，而规则只能提高个别指标、缺全局预见 |
| **解法 1（最务实）** | **规则分层 + 宏模块化**：Global Rule（线平衡、客户承诺）与 Local Rule（区域吞吐优化）分离；用宏模块（macro block）封装可复用逻辑。赛美特 PlantU RTD 的"宏模块 + 拖拉拽建模"就是这条路线 |
| **解法 2** | **把规则加权化**：从"硬优先级链"改为"多因子加权打分 + 门槛值"。交大 PADR 研究证明：用权重与门槛值把各影响因子整体考量来指定加工优序，**优于 FIFO 和 SPT** |
| **解法 3** | **用优化引擎替代部分规则**：数学优化不需要人维护规则，目标变了自己重找解。这是 Flexciton 的核心卖点——"无需调参或调规则" |
| **解法 4** | **数字孪生做规则回归测试**：新 Rule 上线前在仿真环境跑一周，验证对吞吐/CT/WIP 的影响，替代"上线→出问题→回滚"的试错 |
| **指标** | Rule 总数与月增量、规则冲突告警数、规则变更到上线的周期、人工干预（Manual Override）率 |

> **人工干预率是最被忽视的核心指标**。操作员拿着 5~15 分钟前的旧计划去选批，发现 Lot 已 Hold、下一个推荐机台刚宕机——只能手工调整，而手工调整会制造更多"有 WIP 的闲置机台"。**人工干预率 > 15% 基本等于 RTD 失效**。

### 问题 8：光罩寿命/检查触发的隐形停机

| 项 | 内容 |
|---|---|
| **现象** | 罩跑到 Inhibit Limit 被系统硬卡，机台当场停工等送检 |
| **根因** | 派工不看 Reticle 剩余曝光次数，也不排检查计划 |
| **解法 1** | 派工时做 **`剩余曝光次数 ≥ 本批所需曝光数`** 的硬校验（缺这一条就是裸奔） |
| **解法 2** | **Reticle 检查排程纳入调度输出**。AMAT SmartSched 的输出明确包含"Reticle 检查排程"一项，与 Lot/Reticle 搬送指令并列 |
| **解法 3** | 用 Warning Limit 做软约束：接近 Warning 的罩**避免分配大批量**，优先消化小批 |
| **指标** | 因 Reticle 送检的机台停工时长、Inhibit 命中次数（理想为 0）、检查提前完成率 |

### 问题 9：RTS / RTD 耦合失效（傀儡化）

| 项 | 内容 |
|---|---|
| **定义区分** | **RTS（Real-Time Scheduler）= 排程**，解决"什么时候做什么"，输出小时/天级计划；**RTD（Real-Time Dispatcher）= 派工**，解决"现在立刻给谁做"，输出秒级指令 |
| **现象** | RTD 完全照抄 RTS 计划，机台宕机了还在等重排，WIP 原地爆炸 |
| **量化证据** | WSC 2025 仿真：偏差阈值 r = 5 分钟时吞吐量最优；r → ∞（RTD 完全遵循 RTS）时**吞吐量下降超过 50%** |
| **解法 1** | 给 RTD **明确的自主决策权边界**：定义偏差损失函数 `L = max(0, Te − Ta) − max(0, Ta − Te)`，当 \|L\| 超阈值时 RTD 自主决策并反馈 RTS |
| **解法 2** | **做成闭环而非单向流**：RTD 检测偏差 → 实时反馈 RTS → RTS 动态重排 → RTD 按新计划执行。多数厂的现状是 RTD 执行完就完了，RTS 下次还用旧数据，偏差累积到计划彻底失效 |
| **解法 3** | 明确两者的**刷新频率设计**：区域状态变化中 **50% 发生在 5 分钟内、80% 在 15 分钟内**——这是 RTS 刷新周期（10~15min）与 RTD 响应周期（秒级）分层的数据依据 |
| **指标** | 计划执行偏差 \|L\| 分布、RTD 推翻 RTS 的次数与收益、RTS 计划失效率 |

## 三、解决方案技术谱系（L0 → L5）

按成熟度分层，**不要跳级**。跳级的典型后果是：算法上线但现场不信、人工干预率反而上升。

| 级别 | 方法 | 核心机制 | 数据/基础前提 | 收益量级 | 适用阶段 |
|---|---|---|---|---|---|
| **L0** | 静态优先级 + FIFO/SPT/EDD | 单因子排序 | MES 基础数据 | 基线 | 新厂通线期 |
| **L1** | **多因子加权派工公式**（PADR 类） | 权重 + 门槛值综合排序，含光罩/温层/Q-time/负载因子 | 整定时间矩阵、Dedication 表、Q-time 配置 | 明显优于 FIFO/SPT | 爬坡期（**国产厂主战场**） |
| **L2** | **预测型前瞻派工** | WIP 到达预测 + Reticle 预分配，提前 5~15 分钟锁产能 | 可靠的 WIP 预测、ARHS 运力模型 | 显著削减白空间 | 多产品混线期 |
| **L3** | **短周期优化排程（SIS）+ RTD 执行** | 每数分钟产一次局部最优排程，由 RTD 实时微调执行 | 离散事件仿真能力、归一化数据模型 | Litho 利用率 **>+1%**，吞吐 **+2.1%**（AMAT 公开） | 成熟量产 |
| **L4** | **MILP / CP 数学优化** | 精确建模全部硬约束，求最优/近优 | 高质量参数（按机台×罩配对统计的加工时间分布、故障分布） | 相对启发式**额外 +3~5% 吞吐**（AMAT 口径）；Photo 区 **+9.4% 吞吐**（Flexciton/Seagate） | 瓶颈区专项 |
| **L5** | **RL / AI 自学策略** | 从历史调度数据学最优策略，替代人写规则 | 大量带标注的历史决策数据 + 数字孪生验证环境 | 行业在研，公开实证有限 | 前瞻投入 |

### L3 的标准架构（AMAT SmartSched 三件套，值得照搬）

```
[1] 实时数据生成与准备
    从 MES / 其他自动化系统导入明细 → 构建归一化的详细数据模型
         ↓
[2] 基于仿真的预测
    全厂离散事件仿真 → 预测 WIP 及其到达特定工步的时间
    输入：WIP 量、设备状态、计划 PM、产品组合、负载
         ↓
[3] 局部优化短周期排程
    输入：厂状态详细模型 + 预测到达时间 + 上一版排程
    用实时数据构造 Litho 场景约束 → 收窄解空间 → 生成多个候选排程
    目标函数（可配权重）：CT / 工步交期 / Move 目标 / Reticle 移动数 / 稳定性
         ↓
输出：Lot-机台分配 + Lot 加工顺序 + Lot 与 Reticle 搬送指令 + Reticle 检查排程
         ↓
[4] RTD 执行层：秒级按实时状态微调，偏差超阈值时推翻计划
```

**三个设计要点**：
- **"稳定性"必须是目标函数的一项**。用户需要量化"减少排程变动"与其他目标的权衡——排程每次都大改，现场就不信了。
- 输出必须包含**搬送指令**，否则排程在物理上落不了地。
- **预测的价值是"把未来变成当前约束"**：提前知道 WIP 和 Reticle 将在哪里，才能避免把罩锁死在柔性高的机台上。

### L4 的关键工程手法：Reticle Move 与 CT 的"交换比"

Flexciton 的做法极具工程价值，建议**直接移植到 L1/L2 的权重设计中**——核心是把权重定义成**可解释的交换比**，而不是无意义的魔数：

> 设置 `TWCT : Reticle Move = 100 : 75`，含义是：**只有当避免一次搬罩所带来的加权总周期时间增加 ≤ 0.75 小时时，才选择避免这次搬罩。**

实测对比（6 机台 / 48 片 / 4 张罩 / 单机最大批 4 片）：

| 场景 | Reticle 移动次数 | TWCT（48 工步加权） |
|---|---|---|
| 只优化 CT，不惩罚搬罩 | 7 次 | 16.79 h |
| 中等惩罚搬罩（100:75） | **5 次（-28%）** | 18.73 h（+11.6%） |

**可直接用的三条启示**：
1. **把所有权重改写成"交换比"**。`w2 = 0.75 h/次搬罩` 这种定义工程师能讨论、能评审、能和产线谈判；`w2 = 0.3` 没人知道什么意思。
2. **搬罩惩罚不只是时间成本，还有光罩损伤风险成本**。Flexciton 明确提到"潜在损伤风险被认为更高"——这是时间模型里没有的隐性成本，必须显式加进去。
3. 中等惩罚下引擎的行为变化很有启发：**宁愿等低优先级批到达后与高优先级批连跑，也不多搬一次罩**。这正是人工派工想不到、但事后看完全合理的决策。

### Seagate 实测：三指标同时改善的存在性证明

Flexciton 在 Seagate 光刻区（**1600 工步的高重入流程**）单机群实测、真实量产环境、机台内置光罩库、罩可在机台与柜间单独移动：

| 指标 | 结果 |
|---|---|
| 吞吐量 | **+9.4%** |
| Reticle 移动 | **−5.3%** |
| Queue Time | **−4.3%** |

> 这组数据的价值在于**打破"吞吐与搬罩必须权衡"的直觉**。吞吐涨了 9.4% 而搬罩反而降了 5.3%，说明原有的启发式派工在解空间里离最优点很远——**存在大量"又多搬罩又没多产出"的纯浪费决策**。这正是上优化引擎的核心论据。

### 工作负载均衡的轻量解法（EDA + K-means）

针对"光刻机工作负载不均"的专项问题，有一条比全局优化轻得多的路线：

- **按 Pattern Precision 分机台组**，精度数 = 机台组数，Group-g 能处理的最高精度为 Precision-g（高精度组可降级跑低精度活）。
- **把"同罩的所有待加工晶圆"聚合为一个 Job**（`O_au` = 精度 a + 罩 u），天然避免换罩 —— **这个建模技巧很值得学：把"减少换罩"从目标约束变成了问题定义本身。**
- 目标：`min (最长机台工时 − 最短机台工时)`。
- 用 **EDA（分布估计算法）+ K-means 聚类** 求解。

**适用判断**：当你的主要痛点是"负载不均 + 换罩过多"而非"交期与 Q-time 冲突"时，这条路线实施成本远低于 MILP/CP，效果直接。

## 四、TOP 厂商方案深度横评

### 4.1 国际阵营

#### Applied Materials（应用材料）—— APF RTD + SmartSched / SmartFactory

**市场地位**：RTD 市占率最高，存储厂近乎标配，与 AMAT 自家 MES/EAP 深度绑定。

**产品分层（这是全行业最清晰的分层定义，建议作为内部术语标准）**：

| 层 | 职能 | 时间粒度 | 生成频率 |
|---|---|---|---|
| Planning | 计划 | 周~月 | 低频 |
| **Scheduling（排程）** | **Lot 分配**：基于当前与预测的 Lot 到达、当前与未来设备状况，把 Lot 分配给特定区域的设备组 | 12 小时班次 | **10~15 分钟** |
| **Dispatching（派工）** | **Lot 排序**：特定设备上实时的 Lot 加工顺序 | 秒级 | 实时 |

- 全厂实施派工规则，分 **Global Rule**（含线平衡逻辑，管客户承诺）与 **Local Rule**（针对 Litho 等区域的吞吐优化附加逻辑）。
- AMAT 自己的定位表述很精准：**其派工方案可视为"实时排程"，而排程方案是"准实时排程"**。

**Litho 专项能力（SmartSched）**：
- 三件套架构（见上文 L3）；明确解决 **Reticle 未就位造成的白空间**。
- **关键机制**：前瞻避免"把 Reticle 锁死在一台机上，而另一台柔性更低、用同一张罩的机台即将空闲"。
- 输出含 Lot-机台分配、加工顺序、**Lot 与 Reticle 搬送指令、Reticle 检查排程**。
- 目标函数可配：CT / 工步交期 / Move 目标 / **Reticle 移动数** / **稳定性**。

**公开成效**：
- Litho 利用率 **>+1%**，Litho 出片 **+2%以上**，某产线光刻模块吞吐 **+2.1%**。
- 派工方案整体 **吞吐 +5~10%**；再叠加排程与派工集成 **额外 +3~5% 生产力**。
- 优化型排程相对启发式排程**额外 +3~5% 吞吐**（Infineon 案例背书）。
- 214 组产线数据对比纯启发式 RTD：**最高优先级批 CT 改善 ~20%，次高 <5%，低优先级不变**。

**短板**：
- 与 AMAT 自家 CIM 栈绑定深，混栈集成成本高。
- 公开数据多为 2011 年前后的 SmartSched 初代成效，**基线是当年的纯启发式 RTD**，不宜直接对标今天的优化引擎。
- 价格与本地化服务响应是国内客户的主要抱怨点。

**可借鉴的三件事**：① Planning/Scheduling/Dispatching 的三层术语与频率设计；② "稳定性"进目标函数；③ 排程输出必须包含搬送指令与检查排程。

#### Flexciton —— 纯优化路线的代表（Litho 专项实证最硬）

**技术路线**：数学优化为核心 + AI 增强 + **智能分解（smart decomposition）**。不靠规则，目标变了自己重找解——官方口径是"无需工业工程师写初始规则、也无需持续改规则"。

**产品分层**：
- **Flex Planner**：动态产能建模 + 数学优化 → 日投片计划，**每 45 分钟更新一次**。
- **Flex Local**：本地机群排程器，自主平衡组批/CT/吞吐，**无需调参或调规则**。
- **Flex Global**：连接各本地排程器，优化"正确 WIP 的到达"，消除 Timelink 违规、规划最优 Campaign。

> **Global/Local 分层很值得学**：Local 解局部最优，Global 负责"把对的 WIP 在对的时间送到对的 Local"。这恰好对应"重入流下局部最优 ≠ 全局最优"的根本困境。

**公开成效**：

| 场景 | 指标 |
|---|---|
| Photo 区（Seagate，1600 工步，量产实测） | 吞吐 **+9.4%**，Reticle Move **−5.3%**，Queue Time **−4.3%** |
| 扩散区（Renesas，仿真复现量产环境） | Timelink 违规 **−29%** |
| 扩散区组批 | 批量 **+18%** |
| 排程整体 | 全厂吞吐 **+6~8%** |
| 计划层 | 同等 WIP 水平下 CT **−10%**；目标速度标准差 **−30%** |

**规模与可信度**：25+ 个晶圆厂优化项目（美/欧/亚），40 名专注晶圆厂优化的专家，3 项数学优化专利；客户含 Seagate、Renesas、Microchip。部署周期 **6~12 个月**。

**短板**：
- 专注排程/计划，**不是完整 CIM 栈**，必须与既有 MES/RTD 集成。
- 优化引擎的**可解释性**是现场接受度的主要障碍（规则能讲清"为什么这批先做"，优化解不能）。
- 对数据质量要求高：参数不准，优化解就是"精确的错"。

### 4.2 国产阵营

#### 赛美特（Semi-Tech）—— PlantU 全栈，RTD + APS 双轨

### 4.4 一个必须说清的判断：国产差距到底在哪

**不在算法。** 遗传算法、模拟退火、MILP 求解器、CP 引擎——这些国产与国际没有代差，论文里的东西开源求解器都能跑。

**在 Rule 库与量产 Know-How 的积累。** AMAT 的 RTD Rule 模板经过全球数十座 Fab、20+ 年迭代，覆盖几千种生产场景；Litho 区几百条 Rule，每条背后都是真金白银堆出来的经验。

**暴露时点是可预测的**：
- **新厂能用** —— 产品单一、异常少、约束简单
- **产能爬坡期开始吃力** —— 多产品混线、Dedication 冲突上升
- **成熟期暴露短板** —— 异常频发、Rule 覆盖度不足，系统能跑但 CT/WIP 就是比不过

**类比**：算法是发动机，Rule 库是导航地图。发动机再强，没有精准地图也开不到目的地。地图是钱和时间堆出来的，不是代码写出来的。

> **反向推论（对国产方案的机会判断）**：既然差距在规则沉淀，那么**L4 优化路线反而是国产的追赶捷径**——数学优化不依赖规则库，它依赖的是约束建模的准确性和参数质量。这两样可以在 1~2 年内通过扎实的现场工作建立，而 20 年的规则沉淀无法压缩。**这是国产 RTD 最该投的方向，而不是在规则库数量上追赶。**

## 五、Litho 派工指标体系（验收与日常监控）

**第一原则：指标会互相打架，必须显式选主指标。** TWT / OTD / MCT / UOB / Makespan 不可能同时最优。典型实例：用优化算法改善瓶颈后，TWT、OTD、MCT 显著优于 FIFO/CR/EDD，但**瓶颈设备利用率 UOB 改善不明显——要提高瓶颈利用率必须有投料策略配合**。

| 类别 | 指标 | 说明 | 建议目标形态 |
|---|---|---|---|
| **主产能** | Litho OEE / 利用率 | 唯一能对齐财务的指标 | 主目标或硬约束 |
| | Litho Wafer Out / 班 | 直接产出 | 主目标 |
| | White Space 时长及归因 | **必须按原因拆分**：等罩 / 等料 / 等人 / 换罩 / 宕机 / 等检查 | 归因后分项攻坚 |
| **周期时间** | 分优先级 CT（P1/P2/P3 分层） | **总平均会掩盖 Hot Lot 吃掉常规批的问题** | 分层考核 |
| | Litho Queue Time | 队列等待 | 下降 |
| | X-Factor（CT / 理论加工时间） | 跨产品可比 | 下降 |
| **光罩** | Reticle Move 次数 / 班 | 与吞吐权衡，用交换比定权重 | 约束项 |
| | Reticle Wait Idle Time | **机台因等罩空转的时长 —— Litho 最该盯的单一指标** | 趋零 |
| | Reticle 检查导致的机台停工时长 | 寿命管理质量 | 趋零 |
| | Inhibit Limit 命中次数 | 硬卡控被触发 | **必须为 0** |
| **约束合规** | Q-time / Timelink 违规次数 | 良率风险直接暴露 | 趋零 |
| | Dedication 命中率 | 关键层同机达成率 | >99% |
| | 重工回原机台命中率 | — | 高 |
| **均衡** | 机群内机台负载标准差 | CAPPA 的优化目标 | 下降 |
| | 层间 WIP 分布（按光刻层分桶） | 重入流是否失衡；LCONWIP 的管控对象 | 均衡 |
| **系统健康** | **人工干预（Manual Override）率** | **最被忽视的核心指标；>15% 基本等于 RTD 失效** | <5% |
| | 派工决策延迟 P99 | 毫秒级要求，须在真实产能下压测 | 达标 |
| | Rule 总数与月增量 | 规则库膨胀预警 | 监控 |
| | 计划执行偏差 \|L\| 分布 | RTS-RTD 协同质量 | 可控波动 |

> **关于 |L| 的正确期望**：`L = max(0, Te − Ta) − max(0, Ta − Te)`（Te 预计开始、Ta 实际开始）。**真正好的 RTD 不是让 L = 0，而是让 L 在可接受范围内小幅波动**——既有弹性，又不失控。L 恒为 0 说明 RTD 变成了传声筒。

## 六、落地路线图

### Phase 0：诊断（2~4 周，不写一行派工代码）

必须先量化白空间归因，否则后面全是盲调。

1. **白空间归因采样**：连续 2 周，对每台光刻机的每段空闲做归因（等罩 / 等料 / 换罩 / 温层升降 / 宕机 / 等检查 / 等人）。**这张图决定后面所有投入的优先级。**
2. **加工时间分布重建**：按「机台 × Reticle」配对统计，出均值与标准差。不要按机型统计——Nexperia 数据显示同机台不同罩的加工时间差异可达数倍。
3. **约束清单盘点**：Dedication 表（含分级）、Reticle 数量与 Pod 数、Tool Library 容量、Q-time 配置、嵌套 Timelink 清单、Reticle 寿命与检查限。
4. **现状基线**：按第五节指标体系取 4 周基线，**特别是人工干预率**。
5. **Rule 库体检**：数清有多少条、哪些从没触发过、哪些互相冲突。

### Phase 1：止血（1~3 个月）—— 投入产出比最高的阶段

不换系统，只改规则，优先做五件事：

1. **加入 Reticle 在位性权重**：当前机台已有的罩，其对应 Lot 直接加权。这一条通常立刻见效。
2. **加入温层差排序**（CN103390538B 的方法）：注意降温代价远高于升温，用环形差值而非绝对差。
3. **Reticle 剩余曝光次数硬校验**：`剩余 ≥ 本批所需`，不满足直接剔除候选并触发送检排程。缺这条等于裸奔。
4. **Q-time 剩余时间改非线性权重**：剩余 <20% 时权重陡升。
5. **Hot Lot 配额制**：按班限额，超配走审批。这是**管理手段解技术问题**，成本最低、效果最直接。

**预期**：白空间下降、换罩次数下降、Q-time 违规下降。此阶段的收益通常能覆盖后续投入。

### Phase 2：前瞻（3~6 个月）

1. **WIP 到达预测**：先做简单的（基于当前位置 + 剩余工时的确定性推演），不要一步跳到离散事件仿真。
2. **Reticle 预分配**：提前 10~15 分钟下发搬罩指令，与 Lot 搬送指令配对。
3. **ARHS 运力节流**：按搬运系统实际能力限制单次下发的移动请求数 N（IBM 专利的做法）。
4. **机台柔性度权重**：罩优先留给柔性最低的机台。
5. **Campaign 模式试点**：按 Layer Type 给机台分配 4 小时主攻层，设饥饿保护。

### Phase 3：优化（6~12 个月）

1. **选一个机群做 L4 试点**，不要全区上。
2. **权重全部改写为交换比**（`小时 / 次搬罩` 这种可解释形式）。
3. **数字孪生做规则/模型回归**：新逻辑先在仿真跑一周再上线。
4. **RTS-RTD 偏差阈值调优**：从 5 分钟附近开始试，监控 |L| 分布。
5. **建立闭环反馈**：RTD 偏差实时回灌 RTS，而不是单向流。

### Phase 4：自主（12 个月+）

1. 多目标自适应权重（按班次目标自动切换主指标）。
2. RL 策略学习 —— **前提是数字孪生验证环境已经可信**，否则是在真实产线上做实验。
3. 规则库瘦身：把被优化引擎覆盖的规则下线。

## 七、供应商选型 Checklist（Litho 专项，建议直接进技术标）

**A. Reticle 协同能力（最能区分真假 RTD 的部分）**

- [ ] 是否把 Reticle 建模为**带位置 + 容量 + 搬运时延 + 寿命计数**的受限资源？（而非布尔量）
- [ ] 是否支持 **Pod 层约束**（Pod 上机后 Pod 内全部罩只能该机使用；同 Layer 才可同 Pod；Pod 数固定）？
- [ ] 是否支持 **Tool Library 容量**与**临界缓冲水平**（如 8/10 触发清库）？
- [ ] 是否支持 **Reticle 寿命双限**（Warning / Inhibit）与**预测检查限**？
- [ ] 排程输出是否包含 **Reticle 搬送指令**与 **Reticle 检查排程**？
- [ ] 是否按 **ARHS 运力节流**搬送指令下发量？
- [ ] 是否支持 **Dual Reticle** 场景？
- [ ] 是否实现**机台柔性度优先**逻辑（罩留给柔性低的机台）？

**B. 机台与整定建模**

- [ ] 加工时间是否支持**按「机台 × Reticle」配对**配置（而非按机型）？

## 八、避坑清单

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | Reticle 建模为布尔量 | 排出大量物理不可行的派工 | 建模为带位置/容量/时延/寿命的受限资源 |
| 2 | 忽略 Pod 层约束 | 一次 Pod 分配连带锁死多张罩 | 显式建模 Pod，或学 Nexperia 限制每层最多 2 机 |
| 3 | 同型号机台当等效并行机 | 加工时间估计偏差数倍 | 按「机台 × Reticle」统计 |
| 4 | 整定时间不建模或二值化 | **高估性能**；Recipe 数增多误差放大 | 三层整定模型 + 温层值 |
| 5 | 只看当前队列，不看上游将到 | 利用率与产能失衡（组批场景的经典反模式） | 10~15 分钟前瞻 |
| 6 | Dedication 柔性越高越好 | 可靠性差的产线反而更糟（VT 仿真结论） | 柔性与设备可靠性匹配 |
| 7 | 权重用无意义的魔数 | 无法评审、无法与产线谈判、无法迭代 | 全部改写为交换比（小时/次） |
| 8 | 多目标同权优化 | 指标互相打架，什么都没优化 | 显式选主目标，其余转为约束 |
| 9 | Q-time 只做超时报警 | 死锁时无决策依据 | 进目标函数 + 嵌套可行性预检 |
| 10 | RTD 完全服从 RTS | **吞吐下降超 50%**（WSC 2025） | 给 RTD 自主权 + 偏差阈值（~5min 起调） |
| 11 | 规则无限增长 | 200+ 条后维护成本失控 | 分层 + 宏模块 + 定期下线无效规则 |
| 12 | 把智能算法直接套大产线 | 多数算法只在小产线验证过 | 先降维，先单机群试点 |
| 13 | 只优化派工不管投料 | **瓶颈利用率上不去** | 投料（WIP 上限）与派工（WIP 流向）联合评估 |
| 14 | 新 Rule 直接上线 | "上线→出问题→回滚"的试错成本 | 数字孪生跑一周回归 |
| 15 | 不盯人工干预率 | 系统"在跑"但现场已绕过它 | 作为核心 KPI，>15% 即判失效 |
| 16 | 追求非瓶颈区满负荷 | 产出过剩、在 Litho 前堆积 | 非瓶颈省 1 小时无实际效益 |
| 17 | 用"利用率最高"判瓶颈 | 各机台利用率经常非常接近，无法区分 | 用瓶颈率 `b = 任务量/最大产能`，或看计划期末 WIP 堆积 |
| 18 | 认为瓶颈固定在 Litho | 瓶颈随订单量/可用能力/过程控制**会转移** | 瓶颈识别做成在线任务 |

## 附录 A：Litho 派工公式参考骨架（可直接改造）

```python
# 每台机台 M 即将空闲时触发（预测空闲时刻 t_free）
# 权重以"交换比"形式定义，单位可解释

W = {
    'thermal':      0.25,   # 小时 / 单位温层差
    'reticle_move': 0.75,   # 小时 / 次搬罩   ← Flexciton 实证的量级
    'reticle_risk': 0.20,   # 小时 / 次搬罩的损伤风险折算
    'flexibility':  0.40,   # 小时 / 柔性度倒数单位
    'qtime':        None,   # 非线性，见下
    'priority':     2.00,   # 小时 / 优先级档
    'linebalance':  0.15,   # 小时 / 层WIP偏差单位
    'campaign':    -0.30,   # 小时 / 同罩连跑批数（负=奖励）
}

def dispatch(M, t_free, queue, arriving, fab_state):
    # 1. 候选集 = 在队 + 预测窗内到达
    candidates = queue + [l for l in arriving if abs(l.eta - t_free) <= DELTA]

    # 2. 硬约束过滤（任一不过直接剔除）
    candidates = [l for l in candidates if all([
        eligible(M, l.recipe),                    # 机台资格 / 精度等级
        dedication_ok(M, l),                      # 关键层同机 / 重工回原机
        reticle_life_ok(l, M),                    # 剩余曝光次数 >= 本批所需
        nested_timelink_feasible(l, t_free),      # 嵌套 Q-time 窗口全部可行
        pod_conflict_free(l, M, fab_state),       # Pod 独占约束
        layer_assign_ok(M, l, fab_state),         # Campaign 窗内主攻层（可配软化）
    ])]

    if not candidates:
        trigger_starvation_alert(M)               # 机台将空转 -> 上报而非静默
        return None

    # 3. 代价打分（越小越优）
    def cost(l):
        c  = W['thermal']      * thermal_ring_diff(M.current_layer, l.layer)
        c += W['reticle_move'] * reticle_transfer_time(l.reticle, M, t_free)
        c += W['reticle_risk'] * (0 if reticle_on_tool(l.reticle, M) else 1)
        c += W['flexibility']  * (1.0 / machine_flexibility(l.reticle, fab_state))
        c += qtime_penalty(l, t_free)             # 非线性：剩余<20% 时陡升
        c -= W['priority']     * l.priority_rank
        c += W['linebalance']  * layer_wip_deviation(l.layer, fab_state)
        c += W['campaign']     * same_reticle_run_length(l, M, queue)
        return c

    best = min(candidates, key=cost)

    # 4. 搬送指令配对下发（受 ARHS 运力节流）
    if not reticle_on_tool(best.reticle, M):
        if arhs_capacity_available(fab_state, N_MAX):
            issue_reticle_transfer(best.reticle, M)   # 提前 10~15 min
        else:
            # 运力饱和 -> 退回到"罩已在位"的次优候选，避免指令堆积
            onsite = [l for l in candidates if reticle_on_tool(l.reticle, M)]
            if onsite:
                best = min(onsite, key=cost)

    issue_lot_transfer(best, M)

    # 5. 寿命预警联动
    if approaching_warning_limit(best.reticle, best.wafer_count):
        schedule_reticle_inspection(best.reticle)     # 排检查，别等 Inhibit 硬卡

    return best


def qtime_penalty(lot, t_free):
    """Q-time 必须非线性，否则会被 Hot Lot 权重压过"""
    r = remaining_qtime_ratio(lot, t_free)   # 1.0 = 充裕, 0 = 即将违规
    if r > 0.5:  return 0
    if r > 0.2:  return 1.0  * (0.5 - r) / 0.3
    return 50.0 * (0.2 - r) / 0.2 + 1.0      # 陡升区，近似硬约束
```

**三条使用说明**：
1. 权重数值**必须用本厂 Phase 0 的白空间归因数据校准**，上面的值只是量级示意。
2. `machine_flexibility()` 是最容易被漏掉、收益又最高的一项——它的含义是"这张罩除了这台机还能喂几台机"，越少越该优先给。
3. 运力饱和时**退回"罩已在位"的次优候选**，而不是硬等搬罩——这一条在 ARHS 繁忙的 12" 厂里价值很大。
